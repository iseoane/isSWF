## Blocking findings

### B1a — Equivalent resource attribute order creates additive duplicate counters

**Blocking · High confidence**  
`tools/token-native-claude.mjs:27,40–44,93–105`

Resource identity is calculated from `JSON.stringify(resource.resource?.attributes)`. Resource attributes represent keyed attributes, not an ordered series identity.

Static counterexample: export a cumulative input value of 11 with two resource attributes, then export the same resource attributes in reverse order, retaining the cumulative start and advancing the end. The serialized hash changes; therefore group, series and row ID change. `mergeCumulative` treats the second export as a new series instead of replacing the first. Conversion keeps both groups and the report sums them: input becomes 22.

This also bypasses the existing-series reset/order checks. The correction tests do not exercise reordered resource attributes.

**Recommendation:** establish canonical validated resource identity, or visibly reject unsupported identity variation before aggregation. Add an equivalent-resource-reordering regression asserting replacement rather than addition.

### B1b — Consumer still discards cumulative boundaries and launch identity

**Blocking · High confidence**  
`tools/token-native-summary.mjs:144–164`

The converter validates `session`, `series`, `start` and `end`, but its output retains none of those boundary fields. Its row hash includes metadata ID, source, model and group—not cumulative start/end or launch session. Source itself survives only inside the opaque hash.

Consequently, otherwise identical receipts with different valid cumulative boundaries or launch sessions produce identical normalized rows for the same metadata. The report cannot distinguish those measurement boundaries. Categories with different valid start/end intervals can also be combined into one apparently complete row without a coherence check.

This contradicts r3’s segment-identity preservation and leaves V001 B1 only partially resolved. A002’s claim that start/end are retained through the consumer is not visible in the output.

**Recommendation:** preserve sufficient opaque boundary identity and explicit source semantics through the consumer, or reject unsupported/incoherent category boundaries. Add converter/report assertions for changed boundaries, multiple OTLP models/resources and source groups—not only existing result-summary tests.

### B4 — New registered portable tests require POSIX executable mechanics

**Blocking · High confidence**  
`tests/token-native-claude.mjs:98–110,129,155–161`  
Consumer: `tools/check-quality.mjs` unconditionally runs this test.

The fixtures create extensionless `claude` scripts with a POSIX shebang and `chmod`. The helper deliberately selects `claude.exe` on Windows. Thus the fixture does not supply the executable that the Windows helper requests; it either fails or can resolve an unrelated installed executable farther down inherited PATH. The spawn-failure fixture additionally assumes `/usr/bin`.

The two executable-name assertions establish selection only, not the required portable spawn/stdio/platform mechanics. Deferring actual installed-Claude Windows testing does not make this unguarded portable-suite regression acceptable.

**Recommendation:** use platform-supported controlled executable fixtures and deterministic executable absence. Keep POSIX-specific signal evidence explicitly scoped, while verifying the Windows mechanism without claiming native parity.
