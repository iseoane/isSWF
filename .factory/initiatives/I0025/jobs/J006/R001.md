## Decision

**Inference — high confidence:** the right design is to stop trying to turn independently-started cumulative metric series into a shared “one launched process” window. Keep the local OTLP collector only if the intended comparison is explicitly **per-series cumulative state at a bounded capture point**. Do not synthesize a per-process total by coalescing category series with nearby start times. Preserve absent categories as unknown, and compare independent captures only by normalized category/source/model dimensions—not by pretending their series identity or collection intervals match.

A setup-selected project launcher is the only supplied design that can opt in to native telemetry for ordinary interactive Claude CLI usage without silently changing plain Claude, imposing global activation, or requiring extra model calls. It does not capture launches that bypass it, and it is not a safe default until managed-policy permission and actual platform behavior are established. If the acceptance requirement instead insists on a process-complete outcome or plain `claude` capture, **the supplied evidence does not support a minimal defensible implementation**; block rather than inventing an API or adding a daemon.

## Findings

### 1. Native and official counter contract

**Observed official documentation:** Claude’s `claude_code.token.usage` metric reports token counts in four categories: `input`, `output`, `cacheRead`, and `cacheCreation`. Input excludes prompt-cache reads/writes; cache creation combines both cache lifetimes. The documented `query_source` categories are `main`, `subagent`, and `auxiliary` (official monitoring snapshot, “Token counter,” lines 718–724; metric table around lines 644–649). These are subsystem categories, not individual agent identities. The docs separately describe per-request `agent_id` and parent IDs in tracing, but those are not the metric identity promised by the token counter. Enabling traces or detailed logs to derive individual agent identities would add data and is not warranted here.

**Observed official documentation:** the SDK’s `usage` result field counts only the main agent loop; `modelUsage`/`model_usage` covers the whole tree, including subagents (SDK cost-tracking snapshot, “Get the total cost of a query,” around lines 88–111). Streaming results have nuanced scopes and reset behavior: `/clear`, `/reset`, and `/new` reset totals; resumed sessions carry earlier spend; crash recovery may zero final totals. These SDK result semantics are not proof that an ordinary interactive CLI exposes a final result object to an external launcher. SDK totals are not billing authority.

**Observed implementation:** the collector keys each metric series by selected resource attributes, `query_source`, model, and category, and retains each point’s own `startTimeUnixNano` and `timeUnixNano` (`tools/token-native-claude.mjs`, `countersFrom`, lines 43–73). It requires monotonic cumulative temporality, rejects duplicate series, replaces later snapshots rather than summing them, and rejects start changes, non-increasing end times, or decreasing values (`mergeCumulative`, lines 116–130). This is sensible for one continuing cumulative series.

**Key distinction:** each category is a distinct time series. OTLP start timestamps identify that series’ aggregation start, not a shared process-start boundary across categories. OTLP cumulative streams, reset handling, and start-time semantics are defined per stream/series, not as a guarantee of synchronized category starts (OpenTelemetry Metrics Data Model snapshot, “Sums,” “Resets and Gaps,” “Cumulative streams: handling unknown start time”; SDK snapshot, aggregation/series start timestamp and collection sections). A later export updates a given series; it does not make separate series’ accumulated values share a common interval.

**Unknown:** no installed Claude build’s implementation or real ordinary interactive session was independently inspected. Official mutable docs are not installed-CLI proof. The exact installed version’s export/flush behavior, metric temporality/start behavior for all platform/version combinations, whether any series begins later for a given category, and whether a clean final export always arrives are not established. Supplied numeric observations demonstrate concrete timestamps, but do not establish general synchronization guarantees.

### 2. Current implementation, contradiction, and costs

- **Parser and ingress:** `tools/token-native-claude.mjs`, `canonicalAttributes`/`timestamp`/`countersFrom` lines 15–74 validates scalar OTLP attributes, metric type/temporality, values, timestamps, and selected attributes; unknown category/source points are skipped. The scalar type boundary is materially sound. OTLP `AnyValue` supports compound values, but rejecting those is a safe constrained identity domain, not evidence that the protocol itself only supports scalars (`otlp-common.proto`, `AnyValue`; OTLP protocol snapshot, JSON encoding).
- **Cumulative state and receipt:** `mergeCumulative` lines 116–130 correctly replaces cumulative values, does not turn missing points into zero, and fails closed on reset, replay, or changed start. `persistReceipt` lines 132–164 uses a bounded, project-contained private directory and exclusive files/lock. The launcher/config/server/shutdown path is `run`, lines 166 onward: it sets a 1-second export interval, accepts at most 1 MiB total request bytes, 100 rows, at most two concurrent requests, and limits receipt/storage. It retains no receipt on any rejected payload or no token points. Long-lived interactive sessions can therefore incur repeated exports and hit the aggregate ingress cap even when each export is small; that cap is not a general session-duration guarantee. Exactly how many exports typical sessions generate is unknown and was not measured.
- **Converter defect:** `tools/token-native-summary.mjs`, `normalizeClaudeOtel`, lines 144–169 groups by source/model/resource group but compares each start with the current maximum and advances the stored start. A group of starts `1,2,3` passes the ≤1ns check at each step while spanning 2ns; reversed order `3,2,1` fails. This is a static counterexample, not an executed reproduction. The output discards the category-specific boundaries and emits a synthetic segment with maximum start and shared end.
- **Retained misdiagnosis:** V005 records the cited pair `1793704489527000000` and `1793704489528000000`, a **1,000,000 ns (1 ms)** gap, not 1 ns. The converter’s `>1n` check still rejects that pair if they are in the same group. A subsequent 26-token PASS was a separate run and cannot establish that the original failing receipt was fixed. Neither the tolerance nor choosing the maximum start establishes that cumulative values represent the resulting intersected interval. This is a root-model error, not a threshold problem.
- **Consumer/report:** `normalizeClaudeOtel` emits one row per source/model/resource group, maps cache creation to `cacheWrite`, labels scope `unattributed`, hashes an opaque segment, and attaches operator-supplied run metadata. This erases per-series start identity while suggesting a combined interval. `tools/token-report.mjs`, `normalize`/`summarize`/`compare`/`report`, lines 16–108, validates controlled fields/provenance, preserves unknown counters, and bounds output. Independent launch comparison is useful, but its metadata/window assertions are operator-entered, not proof of native collection windows. `source`/`segment` must remain restricted to native provenance.
- **Tests and setup:** `tests/token-native-claude.mjs` covers replacement, missing-series behavior, reset/replay/start-change, privacy/scalar validation, and basic counter extraction (notably lines 11–59); it does not cover permutations or chained category starts. `tests/token-report.mjs`, `tests/token-native-usage.mjs`, and `tests/token-native-auto-pi.mjs` cover report and cross-host consumers; fixtures do not prove live telemetry. `tools/project-state.mjs`, `tools/check-quality.mjs`, `.agents/skills/isswf-setup/SKILL.md`, and English/Spanish operations docs require reopening before implementation to reconcile setup and readiness claims. Setup currently configures project opt-in; there is no evidence here that direct/plain Claude is captured.
- **Platform/resource uncertainty:** Node’s process contract documents `spawn` and stdio/cancellation, and Windows-specific behavior differs (official Node 24 `child_process` snapshot, `spawn`, cancellation, Windows sections). Source code selects `claude.exe` on Windows and uses inherited stdio, but that is not proof of Windows TTY, signal, descendant shutdown, or successful native capture. The supplied record says actual Windows, TTY, native children, and managed-policy/local-only compatibility are unverified. Native fixture success used Claude 2.1.312 with a synthetic loopback provider, not live engineering usage or billing. Latest portable full quality timed out 124; separate `nativeHostDelegation` was NOT_RUN; do not describe either as passing.

### 3. Alternatives and trade-offs

| Option | Fit and limitation |
|---|---|
| **Native metrics through a setup-selected foreground launcher** | Supports ordinary interactive CLI use *when launched through the opt-in path*, with bounded numeric telemetry and no transcript/model call. Local loopback avoids external export. Still incurs periodic ingress; depends on telemetry/policy permission and flush behavior; does not cover plain launches or guarantee complete final capture. Current converter must not fabricate a shared interval. |
| **Native SDK/headless result counters** | Official SDK result semantics offer useful whole-tree totals, but require use of the SDK/query lifecycle or headless `-p` path, not transparent capture of a normal interactive launch. Result completion, resume/reset, and crash semantics complicate comparison. Do not redefine normal use as headless or assume an interactive CLI result API. |
| **Prompt/result events, traces, raw bodies, or per-agent IDs** | More attribution/detail but substantially more privacy, cardinality, and policy burden. Raw bodies can contain entire conversations; logs/traces are not necessary for aggregate token comparison. Reject for this need. |
| **Global settings, daemon, monkey-patching, extra dispatch/model call** | Violates stated scope/authority or adds unbounded lifecycle/integration burden; no supported minimal contract supplied. Reject. |
| **Manual copied totals** | Explicitly not automatic, and vulnerable to omission/transcription; does not meet requirement. |

Official monitoring docs say telemetry is opt-in, exporter variables can be governed/overridden by managed settings, and repository settings cannot enable the exporter. Defaults include a 60-second metric interval; the implementation’s 1-second interval is a deliberate increase in cadence (snapshot, “Quick start,” “Administrator configuration,” “Common configuration variables,” “Metrics cardinality control”). The docs caution that lower cardinality reduces performance/storage cost, and identify sensitive logging options. The local receiver and selected disabled logs/traces reduce exposure but do not prove organizational permission. Managed policy is not inspected by current code; opt-in needs explicit policy readiness, not merely a warning.

## Minimal recommended contracts

**Inference — recommended reconciliation:**

1. **Ownership/lifecycle:** preserve the explicit per-project setup opt-in and foreground launcher; plain `claude` remains unchanged. The launcher owns one random capture identity, one local loopback receiver, one Claude child, and bounded receipt persistence. Do not claim telemetry for bypass launches. Keep inherited stdio and fail safely if telemetry configuration conflicts or capture is not permitted.
2. **Data model:** treat each `(resource identity, source, model, category)` as its own series with its own start/end/value. Capture identity is a local run/capture ID, distinct from native series identity. Store last cumulative value per series; do not sum snapshots. Categories absent from export remain unknown, not zero.
3. **No category coalescing:** remove the assumption that category series share a start. Consumer rows should either retain category-level series values/boundaries, or aggregate only values while explicitly marking interval/source coverage unknown. Do not issue a purported per-process delta unless an evidenced native boundary supplies one. For cross-launch comparison, compare category totals/knownness only under explicit operator-selected comparison metadata; never compare series hashes or timestamps as cross-launch identity.
4. **Reset/failure:** within a capture, retain fail-closed reset, replay/order, duplicate-series, size, and path checks. A changed start/reset invalidates that capture; do not silently begin a new segment and combine it. No export/partial export/rejected point/early child exit means incomplete or absent receipt, with explicit reason; it must not masquerade as zero usage or a complete process outcome. Preserve process exit/cancellation separately from capture completeness.
5. **Privacy/policy/platform:** allowlist numeric categories and bounded model/source labels, exclude prompts/results/auth/session/account/repository identifiers, keep receiver loopback and credentials ephemeral, and persist only the project-local bounded receipt. Make managed-policy compatibility an opt-in prerequisite, not a runtime assumption. Support Linux and Windows only after portable launcher and actual native behavior are verified; Node docs alone do not settle it.
6. **Consumer changes:** reconcile `normalizeClaudeOtel`’s group/segment semantics, report row scope/window/provenance fields, summary comparison behavior, setup readiness messaging, and bilingual operations guidance. Maintain Pi’s existing tree/window contract unchanged. Comparison must distinguish complete/incomplete/missing data and category unknowns rather than infer coverage.

This removes the faulty premise (one shared interval across separate cumulative streams). A tolerance adjustment, minimum/maximum start, or order-independent “cluster” would still invent temporal alignment.

## Bounded verification and stop rules

One finite implementation outcome, if subsequently authorized: support **partial, per-series numeric snapshots** from a setup-selected launch and compare known categories across launches. Do not promise process-complete totals, individual subagent IDs, billing, or plain-launch capture.

Decisive tests before any acceptance claim:

1. Feed independently started categories with differing starts, including the cited 1ms pair; test all permutations and chained starts. Assert no fabricated shared interval or order-sensitive acceptance.
2. Verify cumulative replacement, missing category unknown, replay/out-of-order rejection, reset invalidation, repeated exports, and independent launch identities.
3. Verify OTLP scalar allowlist, malformed/compound/ambiguous AnyValue rejection, no source/segment on non-native provenance, and no raw/private attributes in persisted output.
4. Verify comparison preserves unknownness and does not treat differing native series IDs/timestamps as common launch identity.
5. Verify setup opt-in/plain Claude unchanged, child exit/cancel and partial export semantics; exercise the native entry and portable process tests on Linux and Windows/TTY before claiming parity.
6. Establish managed-policy permission and local-only endpoint compatibility for the actual supported environment before enabling capture; verify bounded long-session ingress/storage behavior without weakening limits.

**Stop/block:** if product acceptance requires whole-process totals from this metric or coverage of launches that bypass the selected wrapper, no supported contract here meets it. Also block on policy conflict, unresolved platform-native failure, inability to distinguish incomplete from zero data, or inability to bound long-session collection/storage. No automatic correction/review retry loop is warranted.
