## Findings

### Observed facts

**Pi — supported native summary exists, but is a current-branch snapshot, not a proven bounded window.** Installed pi-subagents documentation describes event-bus RPC `cost`, returning version 1 with parent usage, child rows, child total, total, and `unresolvedAsyncChildren`. It says the collector walks the current session branch and existing run artifacts, should be called at turn boundaries rather than on a timer, and a child total with unresolved children is a lower bound. It advertises `ping.capabilities.cost`. The package implementation collects parent assistant/compaction usage from the branch, child usage from persisted results and artifacts, and returns parent + child total. Child usage rows have input/output/cache read/write, cost, and turns. The source’s normalization defaults missing fields to zero, and it omits children with no nonzero usage; therefore the output alone does **not** prove provider-reported zero versus missing data. Source: `pi-subagents/src/slash/subagent-cost.js`, especially `usageFromValue`, `metadataUsage`, `collectSubagentCost`, and final aggregation.

**Pi — access requires a host integration.** The documented cost mechanism is in-process extension event-bus RPC, not a direct coordinator cost tool. The Pi extension docs establish extensions can register commands and run in-process, with host permissions; the pi-subagents docs establish the event-bus RPC request/reply contract. The existing coordinator has no direct costRPC tool per the supplied brief. An opt-in local extension command that invokes the documented RPC and emits only allowlisted numeric data is plausible, but is new host code and would require authorized loading/registration. The source collector’s internal ability to read session branch/artifact data is not authority for a new raw-session reader.

**Pi version scope:** task-supplied installed versions are Pi 1.5.0 and pi-subagents 0.83.0. The Pi host guide describes 0.83.0 with Pi 1.4.0 as the exercised integration combination; that is not evidence of a failure on 1.5.0, but requires compatibility verification. The extension and package source are locally installed evidence, not Windows parity or a cross-platform guarantee.

**Claude — inspected local declarations are not enough to substantiate the requested summary.** The locked `sdk-tools.d.ts` declares an `AgentOutput` with `usage.input_tokens`, `output_tokens`, nullable cache-creation and cache-read token counters, and other fields. The same result shape includes `prompt` and optional worktree path, so any use must positively filter fields before retention. These declarations do not, by themselves, prove that isSWF’s coordinator can access them, that they represent all child work, or what `input_tokens` excludes. Nor do they supply verified whole-tree/coordinator totals. The locked package is 2.1.299; task-supplied installed Claude is 2.1.312. That mismatch remains material.

The plan describes Claude Agent SDK `modelUsage` as a whole-tree summary distinct from parent-only `usage`, and identifies status-line context values as latest-response context rather than cumulative consumption. Those are supplied plan claims, not independently rechecked against current documentation or a live installed output. Claude OTel activation is not an acceptable assumed solution here: task inputs note possible account/session/resource identifiers and disallow activation. No raw stream-json retention/parser is selected or supported by this research.

**The existing report is an offline normalizer, not a collector.** `tools/token-report.mjs` accepts only explicit version-1 window summaries, allowlists fields, rejects overlapping tree and row scopes, preserves null counters, and bounds inputs and outputs. It expects one row per actor or an explicitly scoped tree row, and cannot accept a tree row alongside other rows for the same window. Its `native-*` provenance labels do not establish that a native API was actually read: the report claim explicitly describes curated supplied summaries and no native collection. `tests/token-report.mjs` covers arithmetic, partial/unknown counters, tree/unattributed scopes, privacy rejection, duplicates, overlap, limits, and CLI behavior using fixtures; it is not a test of native host behavior.

### Inferences and recommendations

1. **Smallest credible Pi candidate:** an explicitly opted-in Pi extension command on the coordinator’s own session that invokes the supported `cost` RPC at a user-selected boundary and emits only bounded numeric receipt rows. Its benefit is avoiding a new Pi session parser and reusing the native parent/child summary. Its cost is a new extension integration, opt-in loading/registration authority, compatibility checks for Pi 1.5.0 + subagents 0.83.0, and explicit window semantics. A single cost snapshot is not a measurement window; cumulative branch totals, resumes, and resets need supported start/end snapshots and verified delta rules, or the receipt must honestly represent a single native snapshot rather than claim a delta. Missing-vs-zero and unresolved-child coverage must remain explicit; the existing RPC shape may not carry enough missingness detail to satisfy that without a verified additional contract.

2. **Claude remains the blocking path for the full objective.** An explicitly supplied, sanitized native numeric receipt is the least invasive candidate, but the available evidence does not establish a coordinator-plus-child source that produces one. Do not infer an Agent SDK result is the active host coordinator’s accessible receipt, or infer per-child rows from a tree summary. A Claude metric-only native mechanism or filtered final result is a proposal, not currently demonstrated feasibility. The full cross-host objective should not be silently narrowed to Pi plus manually entered Claude data.

3. **Do not claim native parity or full attribution yet.** There is no live native counter observation from this research, no Windows host verification, and no verified Claude 2.1.312 output schema. The existing report fixtures can verify normalization but cannot close those gaps.

### Specific blockers / next evidence

- **Pi window and missingness:** determine, through supported API evidence (not raw session inspection), whether cost snapshots can be differenced reliably across a bounded start/end window and resumes/resets, and whether native reported zero can be distinguished from missing counters. Verify the 1.5.0 / 0.83.0 combination and direct extension access to event-bus RPC.
- **Claude native scope:** obtain an approved, sanitized schema/example or existing native numeric receipt for the installed 2.1.312 coordinator and child results. Establish counter semantics, coordinator availability, child inclusion/identity, cumulative versus latest values, and how data can be supplied without retaining prompt/tool/auth fields. Reconcile locked 2.1.299 declarations separately; they are not proof for installed 2.1.312.
- **Product scope decision if evidence remains unavailable:** operator must explicitly decide whether to block full native Pi/Claude coordinator-and-child support or authorize a narrower outcome. Research does not make that decision.
- **Platform:** native Windows evidence remains unavailable; keep it an explicit verification blocker, not a parity claim.
