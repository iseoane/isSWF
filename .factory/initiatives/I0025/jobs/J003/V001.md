## Blocking findings

### B1 — Cumulative snapshots are emitted as curated windows

**Location:** `tools/token-native-summary.mjs:88–102`; corresponding examples in `docs/en/operations.md:92–96` and Spanish mirror.  
**Confidence:** high. **Axes:** Standards and Spec.

Without `start`, the converter copies the cumulative Pi counters and unconditionally returns `mode: 'window'`. Neither the output schema nor its rows retain a cumulative-snapshot distinction. Calling the window `snapshot` is only an arbitrary identifier.

**Concrete condition:** take a Pi snapshot after earlier work, convert it without `--start`, and supply acceptance metadata for the latest task. The converter emits all prior counters as that task's window. The unchanged report accepts it and computes `tokensPerAccepted`; it cannot distinguish this input from a real bounded delta. The first documented example explicitly follows this path into `token-report`.

Claude final results also require a visible cumulative/resume boundary: the supplied upstream contract says resumed results can include earlier totals, but the converter always emits a window.

This violates r2's explicit requirement that a snapshot alone remain a labelled cumulative snapshot, not a fabricated window.

**Smallest fix:** preserve standalone snapshots in a distinct bounded snapshot format that cannot enter the existing window arithmetic unchanged. Emit report windows only after supported boundary validation; refuse unsupported resumed Claude windows rather than relabelling cumulative totals. Correct both guides.

**Focused verification:** assert that a standalone cumulative snapshot cannot produce an ordinary accepted-outcome window; assert valid Pi start/end conversion still works. Cover resumed/cumulative Claude input according to the supported restricted contract.

### B2 — Standalone Pi conversion leaks arbitrary counter fields

**Location:** `tools/token-native-summary.mjs:36–41,88,102`.  
**Confidence:** high. **Axes:** Standards and Spec.

`piRows` checks four named numeric properties but returns the original rows. The standalone path retains the original `counters` object, and final output assigns it directly.

**Concrete condition:** add `prompt: "PRIVATE"` or a nested private payload to an otherwise valid Pi receipt's `rows[0].counters`. Validation succeeds, and the converter serializes that extra property to stdout. No invalid numeric value is required.

This breaks the allowlist/privacy boundary before the report is invoked. It also breaks consumer compatibility: `token-report.mjs:24` rejects counter objects containing unknown fields. An extra payload can additionally exceed the report's 4 KiB row limit while remaining below the converter's overall output limit.

**Smallest fix:** construct a fresh counters object from precisely the four validated numeric fields at the Pi input boundary. Do not forward the original object. Reject unsupported shapes or drop extras before emission.

**Focused verification:** inject private extra fields at receipt, row and counter levels; inspect the converter output itself, then feed valid normalized output through the real report. Require no sensitive fields and consumer acceptance.

### B3 — Constant model-mixture identity permits incompatible comparisons

**Location:** `tools/token-native-summary.mjs:45–61`; consumer `tools/token-report.mjs:72–77`.  
**Confidence:** high. **Axes:** Standards and Spec.

Claude model names are discarded and every result receives `model: 'model-mix'`. There is no model-set fingerprint or allowlisted breakdown.

**Concrete condition:** normalize two supplied results with the same session ID and matching comparison metadata, but change `modelUsage` from one model set to another. Both outputs have the same tree ID and `model` value. With known counters and a positive baseline, the report considers them comparable and emits numeric reductions despite the changed models.

This is not merely missing display detail: the report relies on the model field to enforce compatibility. r2 explicitly permits a model-mix **fingerprint**, not one constant label that erases incompatible identities.

**Smallest fix:** encode a deterministic, bounded fingerprint of the relevant native model identities in the existing model field, retaining the single inclusive tree row. Do not fingerprint token amounts as model identity. If identity cannot be established, prevent a matched-comparison claim.

**Focused verification:** pass normalized results through `report(after, before)` and assert changed model identities yield `incomparable`, while reordered equivalent model entries remain compatible.

### B4 — CLI invents Pi host version when none was observed

**Location:** `tools/token-native-summary.mjs:120`.  
**Confidence:** high. **Axes:** Standards and Spec.

When `--host-version` is omitted, Pi output claims `1.5.0`, regardless of the receipt's version or the actual host. The extension deliberately records `unknown`, and the documentation says to supply a version only when independently observed.

**Concrete condition:** convert the extension's ordinary unknown-version receipt without `--host-version`. Output silently changes the claimed host version to `1.5.0`. The same happens for another supported host version.

**Smallest fix:** default to `unknown` or a validated observed receipt version; retain an explicit caller-supplied override as declared metadata. Never infer host version from this development environment.

**Focused verification:** omit the option and assert no known version is invented; cover an explicit observed version.
