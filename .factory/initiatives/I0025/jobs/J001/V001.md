## Blocking findings

### B1 — Shared accepted outcomes are counted once per agent
**Paths:** `tools/token-report.mjs:54–56`; `tests/token-report.mjs:9–14`; `docs/en/operations.md:54`; corresponding Spanish guidance  
**Confidence:** high. **Axes:** Standards and Spec.

The denominator is the sum of every row’s `accepted`, irrespective of shared window/candidate/outcome identity.

The existing fixture demonstrates the defect: both agent rows describe `w1`, `c1`, `o1`, and `accepted: 2`. Their processed total is 310. The test requires **77.5**, obtained by counting four acceptances, although the same supplied window/outcome acceptance count is two. Counting its participating agents must not multiply product acceptance; the shared denominator would yield **155**.

The schema/documentation supplies no rule for allocating mutually exclusive acceptance counts across agent rows, and repeating a window-wide count is consistent with the documented instructions.

**Required correction:** define acceptance ownership at the outcome/window level, count shared acceptance once, and reject contradictory declarations. Update EN/ES instructions and independently hand-calculated tests covering coordinator/worker/review/correction rows contributing to one accepted outcome.

### B2 — Whole-tree rows are incorrectly labeled attributed
**Path:** `tools/token-report.mjs:56`  
**Confidence:** high. **Axes:** Standards and Spec.

Attribution is determined solely by whether any row has `scope: "unattributed"`. A valid single `scope: "tree"` row therefore emits:

```json
"attribution": "attributed-rows-only"
```

A whole-tree aggregate does not establish individual-agent attribution. This contradicts r3’s requirement to keep unavailable attribution/coverage visible and the accepted distinction between whole-tree totals and actor rows.

**Required correction:** distinguish aggregate/tree coverage from individual attribution and unknown coverage. Preserve useful aggregate totals without implying they are individually attributed. Add a whole-tree-only output assertion.

### B3 — Comparison permits 200 rows despite the 100-row total limit
**Paths:** `tools/token-report.mjs:18,69–71,94`; `tests/token-report.mjs:42`  
**Confidence:** high. **Axes:** Standards and Spec.

`MAX_ROWS` is enforced independently by each `normalize` call. Comparison mode loads and normalizes two inputs, so 100 before rows plus 100 after rows pass the row-count checks. Compact metadata permits the emitted after report to remain below the separate output bound.

r3 explicitly requires **100 rows total**, not 100 per file. The existing 101-row test exercises only a single input.

**Required correction:** enforce the combined comparison row budget and add CLI tests at 100 combined rows and 101 combined rows, with both individual files below 100.

### B4 — Positive-baseline guard does not protect reduction arithmetic
**Paths:** `tools/token-report.mjs:64–67`; `tests/token-report.mjs:32–33`  
**Confidence:** high. **Axes:** Standards and Spec.

For matching rows with all baseline counters zero, `rawDifference` is still calculated and `processedReductionPercent` divides by zero. A positive after total produces negative infinity in the exported report object; JSON serialization silently converts it to `null`. Status is incomparable, but the reduction calculation itself is not guarded by the required positive baseline.

The named zero-baseline fixture is not a zero baseline: its helper retains output 40, cache-read 30, and cache-write 10. It also compares different actor identities, so it only demonstrates metadata mismatch.

**Required correction:** explicitly suppress undefined reduction arithmetic for a zero baseline; test matching identities with all four baseline counters zero through both exported reporting and CLI serialization. Assert finite defined values or explicit undefined values.
