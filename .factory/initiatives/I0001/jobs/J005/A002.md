## Objective and exclusions

Propose the smallest design that lets workers and successive panel entries share one finite capacity pool, while distinguishing capacity waits, dependency reasons, code integration, and operator acceptance.

Keep permanent logical-job admission distinct from concurrency capacity. Do not assume the separate role caller stores form a global pool. Exclude a scheduler/daemon/registry framework, arbitrary detached-command wrappers, automatic recovery, remote operations, client operations, reboot or cleanup. Unknown cessation must retain capacity.

## Proposed shape

Use one narrowly scoped, operator-owned capacity ledger, explicitly bound by trusted external grants to the participating runtime callers and their shared scope. Do not infer shared scope from a repository path or merge caller stores implicitly.

The minimal interface should provide atomic **try-reserve**, **release-with-verified-evidence**, and **read-state** operations. Reservations represent active execution slots, not permanent job admission. A blocked or human-waiting job with no active attempt holds no slot. Panel entries acquire only when ready, release on completion, and acquire again for the next entry; waiting entries must not hold slots.

The ledger must not release on `terminal.json` alone or an external `cessation=true` assertion. The worker lifecycle reports descendants as `uncertain` or `not-claimed` (worker excerpt, lines 261–309); native recovery has stronger, identity-bound PID-namespace checks (recovery excerpt, lines 133–173). Release only when an integrated cessation contract verifies the relevant execution and descendants have ceased. Otherwise retain the reservation and expose the uncertainty.

Represent dependency satisfaction separately from plan status and operator acceptance. A code dependency is unblocked only by evidence that its named contract is integrated. `awaiting-human` can release execution capacity but does not satisfy that dependency. Detect cycles before execution; a blocked job must not prevent unrelated runnable work from using available capacity.

## Ordered functional units

1. **Define the capacity and dependency contracts.** Specify the shared-scope binding, slot limit, reservation identity, atomicity, lifecycle hooks, cessation evidence, and distinct dependency reasons. Treat the specification’s initial limit of two as a proposal pending confirmation, not an authorized runtime budget.  
   **Acceptance:** The contract distinguishes permanent admission from temporary capacity; defines when slots are acquired and released; and makes unknown cessation, code integration, and operator acceptance distinct states.  
   **Verification:** Review the contract against the cited source excerpts and the relevant full specification.

2. **Integrate one shared capacity seam.** Make worker admission and panel execution use the same explicitly bound ledger; preserve per-job writer isolation and existing permanent admission behavior.  
   **Acceptance:** Two compatible isolated jobs can proceed within the finite limit; duplicate writers and dependency cycles block; one blocked job does not block unrelated runnable work; a human-waiting job without an active attempt releases its slot.  
   **Verification:** Deterministic concurrent tests for atomic reservations, duplicate writers, cycles, unrelated progress, and unknown-cessation retention.

3. **Add successive panel-slot behavior.** Panel entries use the same pool as workers and acquire/release one slot at a time without holding capacity while waiting.  
   **Acceptance:** Successive entries finish under one finite limit without deadlock or exceeding the shared limit.  
   **Verification:** Synthetic contention test with workers and multiple panel entries; assert reservation counts and release evidence at each transition.

**Dependencies and unblock conditions:** Unit 2 depends on Unit 1’s integrated contract. Unit 3 depends on the shared reservation contract being integrated. Implementation and tests remain unassigned; each requires coordinator adoption and its own authorized dispatch.

## Review, checkpoints, and risks
