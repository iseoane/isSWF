## Findings

### F001 — Verified manager Git root does not establish an installed release

**Blocking · introduced · high confidence**  
**Location:** `.agents/skills/isswf-coordinator/SKILL.md:14–16`

Line 14 expressly makes a manager-installed Git package eligible when its registered installation root is verified. Line 16 then obtains its version from the local manifest. These conditions establish package location and metadata, not release identity.

Pi’s installed implementation supports ordinary branch/ref Git checkouts. `getInstalledPath()` checks whether the computed path exists (`dist/core/package-manager.js:699–707`); `listConfiguredPackages()` exposes configured sources and those paths (`:786–808`). Neither verifies that the checkout represents a release. Its normal Git installation path also does not distinguish refs (`:1902–1921`).

**Semantic counterexample:** a manager-installed development branch contains the expected package name and literal `1.8.2`, but has no independently established release identity. It meets the explicit Git eligibility rule and can be reported as running release `1.8.2`. The same development checkout loaded through a local path becomes unknown. Thus packaging topology, rather than release evidence, changes the classification.

This contradicts the required separation between source checkouts and installed releases. The generic “unverifiable provenance” fallback does not repair an explicit rule declaring a verified Git root sufficient.

**Recommendation:** distinguish manager ownership/location from release provenance. Specify the additional locally verifiable release evidence required for Git installations, or keep those installations unknown. Apply the same distinction to running identity and installed candidates. Do not require a particular receipt format unless that is the supported release contract.

**Class search:** searched the shared agent resources for `manager-installed Git`, `installed-release provenance`, and `newest locally installed`; the operative instances are concentrated in these added paragraphs.

### F002 — Configured inventory is insufficient for the unqualified newest-installed claim

**Blocking · introduced · high confidence for Pi**  
**Location:** `.agents/skills/isswf-coordinator/SKILL.md:16–18`

The procedure permits only `pi list` inventory, but the inspected implementation enumerates packages configured in the current user and current project settings—not every locally installed package.

**Semantic counterexample:** project A runs installed release `1.8.2`; project B has project-local installed release `1.9.0`. Running `pi list` from A does not enumerate B’s installation. If A’s visible inventory contains only `1.8.2`, the procedure takes the equal-version branch and emits nothing, despite a newer locally installed release.

The instruction neither establishes inventory completeness nor qualifies its “newest locally installed” claim. Missing candidates are not detected as missing or ambiguous records, so the existing unknown fallback does not cover this case. Multiple candidates also lack an explicit maximum-selection/completeness rule.

This is a substantive gap in the accepted advisory, not a request for arbitrary directory scanning. Claude inventory completeness likewise remains unestablished by the supplied grounding; the confirmed Pi gap alone blocks cross-host acceptance.

**Recommendation:** establish the exact supported inventory boundary and completeness guarantees. If it cannot represent all installations required by acceptance, report that limitation explicitly rather than silently treating the visible subset as sufficient. Narrowing the accepted outcome requires a coordinator/operator decision, not reviewer inference.
