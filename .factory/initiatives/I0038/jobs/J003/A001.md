## Proposed functional contract

### Invocation and ownership

Use existing supported setup entry points:

- Pi: `/skill:isswf-setup`
- Claude Code: `/isswf:isswf-setup`

For an explicitly requested native update, show the exact configured source/scope and intended effect before confirmation:

- Pi: `pi update <configured-source>`. Fixed references require an explicitly selected replacement reference.
- Claude: `claude plugin update isswf@isswf`; marketplace changes are separate authorized effects.
- Reload/restart is a separate step. Manager success does not prove that the current session loaded new bytes.
- Never use `pi remove` or Claude uninstall as old-version cleanup.

A user-scoped update affects other projects. If their active work cannot be reconciled, provide the proposal but refuse application. No setup record or operator attestation is technical proof of global inactivity.

For explicit legacy maintenance, retain the existing installed-release `inspect` → confirmed `migrate` contract, including expected digest, clean affected pin, transaction ID and external-writer reconciliation. Do not route normal native setup through it.

### Minimal usage data

A project-local entry in the existing setup record can record **that project’s observed use**, but cannot alone satisfy a shared `project → version` registry.

If shared tracking is approved, the smallest justified addition is **one private, bounded registry per selected maintenance domain**, not a machine-wide scanner:

- Canonical project identity/path, host and scope.
- Identity kind: native managed package, legacy runtime, source checkout, or unknown.
- Observed version and provenance; exact legacy runtime ID/format where applicable.
- Last reconciled usage and immediately previous successful identity.
- Explicit unknown/unavailable status; no expiry-based eviction.

Keep private project paths out of tracked/public setup records. Native observations are not project pins. Setup refreshes the current project on every run; refusal and unreadable identity must not retain a misleading “known current” entry.

The registry is **not complete by construction**: pre-registry projects, alternative stores/users, moved/offline projects and direct host launches remain outside its knowledge. Missing projects cannot be inferred unused. Scope/completeness reconciliation must be explicit before deletion; “ask” cannot override a positively known in-use version.

No native runtime-store prerequisite should be introduced merely to host this registry. Its private location/domain is an unresolved product contract, not an existing supported capability.

### Cleanup safety

Candidate eligibility must exclude:

1. Running/loaded identities, including unreconciled sessions.
2. Every registered current use.
3. Immediately previous successful identities—not “second-highest semver” or directory mtime.
4. Versions required by active attempts, unresolved operations or retained rollback contracts.
5. Unknown ownership, incomplete inventory, malformed records and inaccessible projects.

For host-owned installations, return `unsupported` with the reason and supported manager guidance; perform no deletion.

For legacy store cleanup, actual implementation would additionally need a store-wide cooperative maintenance claim honored by retention, migration and execution registration. The present per-project claim cannot serialize shared-store deletion. Revalidate candidates and registry generation after confirmation, before effects. Never recursively delete a supplied arbitrary path; derive exact owned targets and handle format-2 directories plus anchors coherently. Interrupted staging and historical journals are not cleanup candidates.

**Important:** existing rollback accepts historical completed migration IDs. Deleting their referenced runtime would weaken that contract. Preserve those references conservatively unless an explicit rollback-retention policy is accepted.
