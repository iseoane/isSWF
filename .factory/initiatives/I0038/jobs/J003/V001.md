**Blocking · introduced · high confidence**

**Locations:** `.agents/skills/isswf-setup/SKILL.md:67,73`; `docs/en/installation.md:110`; `docs/es/installation.md:110`; `docs/installation.md:141`.

The new procedure directs readers to current host help, calling it “read-only,” without requiring verification of the launcher or providing a non-executing fallback. The retained A002 evidence already demonstrates the failure: running `claude plugin --help` through the mise wrapper installed Claude CLI 2.1.322 before printing help, violating the no-install boundary.

Consequently, following the syntax-validation instruction can mutate the environment before update confirmation. The prohibition on installation does not explain how to avoid the demonstrated mechanism.

**Required correction:** Prefer reading version-matched installed documentation/source. Explicitly prohibit executing unverified shims, wrappers or auto-provisioning launchers merely to obtain help or inventory. The incident is disclosed rather than concealed, and no automatic cleanup is warranted. Disclosure does not close the procedural defect or retroactively satisfy the development no-install requirement.

### F002 — Pi’s package selector does not select the proposed registration scope

**Blocking · introduced · high confidence**

**Locations:** `.agents/skills/isswf-setup/SKILL.md:67–75`; corresponding commands at `docs/en/installation.md:106`, `docs/es/installation.md:106`, and `docs/installation.md:137`.

The procedure frames inspection and confirmation around a selected registration/scope, then prescribes:

```text
pi update --extension <exact-configured-source>
```

Installed **Pi 1.5.0 source** establishes a materially broader selector:

- `dist/core/package-manager.js:860–886`: `update(source)` collects matching registrations from **both user and project settings**.
- `:1466–1485`: package identity deliberately ignores npm version and Git ref.
- `dist/package-manager-cli.js:363–370`: `--local` is rejected for update; it is not a missing scope flag that can simply be added.

For example, a project registration and user registration of the same Git repository match even when their refs differ. Supplying the project’s exact configured source does not restrict the update to that project registration. Knowing its source and scope is therefore insufficient to construct the promised bounded operation.

The general “what the manager will replace” gate is directionally correct, but the host-specific command guidance does not explain this concrete expansion or require reconciling its full identity-match set. It permits an apparently project-scoped proposal to overlook a user-scoped mutation and affected projects.

**Required correction:** Document Pi’s actual matching behavior. Resolve every matching registration/source/ref and actual mutation scope before proposing the update. Refuse when the manager’s operation exceeds the confirmed scope or affected-work evidence. Add a static walkthrough/assertion for same-identity registrations in both scopes with different refs. Do not invent a scope flag or alter trust/settings to narrow the operation.
