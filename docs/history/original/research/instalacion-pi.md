## Hechos de Pi 1.2.0

- **El paquete Pi reúne recursos; no los convierte todos en código.** Un paquete Pi puede contener `extensions/`, `skills/`, `prompts/` y `themes/`, descubrir esos directorios por convención o declarar rutas en `package.json` bajo `pi`. Sus recursos se pueden filtrar desde settings. Fuentes: [README.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/README.md#L15-L19); [docs/packages.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#L42-L74) y [#L94-L120](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#L94-L120).
- **Fuentes y pinning.** Pi admite npm, git y rutas locales. Las versiones npm y las refs git (etiquetas o commits) quedan fijadas; `pi update` no mueve una ref fijada. Un paquete local se carga desde su ruta sin copiarlo. Las rutas locales relativas se resuelven desde el archivo de settings que las declara. Fuentes: [docs/packages.md, instalar y escoger fuente](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#L7-L40).
- **Ámbito de instalación.** `pi install <source> --local` registra el paquete en `.pi/settings.json`; sin `--local`, la configuración de paquetes es personal en `~/.pi/agent/settings.json`. Los paquetes declarados por el proyecto se instalan/cargan al resolverse la confianza del proyecto. Pi permite que una entrada de paquete de proyecto reemplace la personal con el mismo identificador. Fuentes: [docs/packages.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#L7-L27) y [#L123-L127](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#L123-L127); [docs/cli.md, comandos de paquetes](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#L250-L290).
- **El trust protege recursos de proyecto, no es sandbox.** Requieren decisión de confianza `.pi/settings.json`, `.pi/skills`, paquetes declarados por proyecto y `.agents/skills` del proyecto. `--approve` autoriza esos recursos para una invocación; `--no-approve` los ignora. En modos no interactivos, sin override ni confianza guardada, el ajuste global `defaultProjectTrust: "ask"` no carga recursos protegidos. Los context files `AGENTS.md`/`CLAUDE.md` son excepción: se leen sin trust. Ni trust ni el working directory aíslan los permisos del proceso. Fuentes: [docs/security.md, trust](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/security.md#L27-L83); [docs/cli.md, prompts and process](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#L221-L244); [docs/configuration.md, context files](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/configuration.md#L41-L48).
- **Una skill es catálogo diferido de instrucciones, no agente ejecutable.** Pi descubre directorios con `SKILL.md`; al inicio anuncia nombre, descripción y ruta, y solo carga el cuerpo cuando la tarea lo requiere. Puede incluir scripts, referencias y recursos auxiliares junto al Markdown. Los scripts se ejecutan como instrucciones de la skill usando las herramientas disponibles; Pi no registra cada script como herramienta automáticamente. Fuentes: [docs/skills.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/skills.md#L1-L35), [#L41-L65](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/skills.md#L41-L65).
- **No hay perfiles de agente Markdown nativos con despacho automático.** Pi declara que omite subagentes y plan mode. Un `AGENTS.md` es un archivo de contexto leído como instrucciones generales, no un registro de perfiles; Pi no documenta autoselección de perfiles por archivos `agent.md`. Añadir agentes o herramientas de ejecución exige una extensión o paquete que aporte esa capacidad. Fuentes: [README.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/README.md#L15-L19); [docs/configuration.md, context files](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/configuration.md#L41-L48); [docs/extensions.md, integrations](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md#L1-L7) y [#L72-L90](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md#L72-L90).
- **Los prompt templates no sustituyen skills o perfiles.** Son Markdown que se convierte en comando `/...` y expande argumentos a un prompt. Sirven para invocar una tarea repetible, sin crear integración ejecutable. Fuentes: [docs/prompt-templates.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/prompt-templates.md#L1-L24) y [#L27-L60](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/prompt-templates.md#L27-L60).
- **Settings de modelo no son settings por rol.** `defaultProvider`, `defaultModel` y `defaultThinkingLevel` controlan arranque; `modelThinkingLevels` asocia nivel de razonamiento a un ID de modelo, no a un perfil factory. `--model` y `--thinking` seleccionan el destino y esfuerzo/nivel de una invocación. No existe en el catálogo de settings un mapa perfil → modelo/esfuerzo. Fuentes: [docs/settings.md, model and thinking](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/settings.md#L7-L25); [docs/models.md, select a model](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/models.md#L17-L35); [docs/cli.md, model options](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#L53-L74).
- **Settings de proyecto se combinan con settings personales.** Pi coloca settings, skills, extensiones y prompts del proyecto bajo `.pi/`. Las rutas de recursos de ese settings se interpretan desde `.pi`; las listas de recursos personales y de proyecto se combinan. Por tanto, agregar un paquete de proyecto no borra por sí mismo skills personales homónimas. Fuentes: [docs/configuration.md](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/configuration.md#L1-L39); [docs/settings.md, resources](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/settings.md#L147-L163).
- **Una skill puede traer un CLI Python sin convertirlo en herramienta Pi.** La guía presenta `scripts/` junto al `SKILL.md` y manda ejecutar scripts usando rutas relativas a la carpeta de la skill. No se requiere extensión por recurso. La guía de paquetes solo recomienda dependencias para código de extensión; archivos/scripts acompañantes no se registran como tools automáticamente. Fuentes: [docs/skills.md, ejemplo y carga](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/skills.md#L9-L35); [docs/packages.md, dependencias](file:///home/iseoane/.pi/agent/install/releases/1.2.0/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#L76-L92).

## Recomendación

**Para el primer arranque, usar copias vendorizadas y versionadas en el repositorio de cada proyecto.** Mantener skills en `.pi/skills/<nombre>/SKILL.md`, sus referencias junto a ellas y el CLI de Python estándar en `scripts/` de la skill que lo usa. Añadir únicamente `.pi/settings.json` si hace falta configurar rutas o defaults del proyecto. El contenido queda en la revisión del proyecto, no depende de `~/.pi/agent/AGENTS.md` ni de un path local externo. El operador inspecciona y confía el proyecto con `pi --approve` o `/trust`; la confianza habilita recursos, pero no limita permisos del proceso. Esta opción es la más simple para validar composición y dependencias de la spec sin introducir instalación, actualización o protocolo de runtime todavía.

**Alternativa de distribución cuando varios proyectos compartan la misma factory:** un Pi package único con skills y scripts, versionado por npm exacto o por ref git inmutable, declarado a nivel proyecto. Instalarlo con `pi install <fuente-fijada> --local` o declarar la misma fuente en `.pi/settings.json`; revisar el origen antes de confiarlo. Así se evita copiar y se centraliza la actualización, pero se añade un paso de resolución/instalación y la carga sigue sujeta a trust. No fijar a una rama móvil como `main` si la ejecución debe reproducirse. Si se usa ruta local, es path-resolved y no portable a otro clon salvo que se garantice esa ruta.

**No instalarlo globalmente.** Una instalación global haría disponibles recursos en todos los proyectos y modificaría estado personal; contradice la petición de no tocar configuración global y dificulta separar versiones por proyecto. Tampoco añadir una extensión, agente o herramienta Pi por skill o script. Si en el futuro se necesita un proceso ejecutable de fábrica, que una sola integración lo justifique por una capacidad que las skills y CLI no puedan asegurar; la decisión de interfaz queda pendiente del diseño de runtime de la spec.

El catálogo de skills cubre anuncios y carga bajo demanda. Los perfiles factory siguen siendo datos/instrucciones propios del producto, no una capacidad Pi que deba confundirse con skills. Mantener explícita esa distinción: perfil selecciona responsabilidad y configuración de ejecución; skill selecciona procedimiento reusable. Los settings de Pi proporcionan defaults de sesión, mientras que el mapeo de roles a modelos y esfuerzo pertenece a la configuración de ejecución que la spec aún no ha diseñado. Al invocar un worker, esa capa debe resolver los valores y expresarlos en opciones de proceso o API compatibles con Pi; no asumir que Pi asignará modelo a una skill.

## Prueba local sin modelo

Se ejecutó un test aislado contra la API exportada `loadSkills` de la instalación Pi 1.2.0. En un directorio temporal bajo `/tmp` se creó `.pi/skills/triage/SKILL.md`; con `cwd` apuntando al proyecto temporal y un `agentDir` temporal, Pi devolvió la skill `triage` con la ruta esperada, sin diagnósticos. No se hizo llamada a modelo, red, GitHub, instalación de paquetes ni cambio de settings reales. El test prueba descubrimiento del directorio de skills a través del loader real, no la resolución interactiva de trust ni la instalación desde Git.

También se comprobó `pi --version` (`1.2.0`) y se consultó `pi --help` para confirmar en el binario local las opciones `--approve`, `--no-approve`, `--skill`, `--model`, `--thinking`, `--offline` y los modos. No se lanzó una sesión Pi con modelo. La guía oficial señala que en JSON/RPC/print la decisión de trust no tiene prompt, lo cual justifica optar explícitamente por `--approve` para una futura sesión de proyecto aprobada, o `--no-approve` cuando se quieran omitir recursos confiables.
