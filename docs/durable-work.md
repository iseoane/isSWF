# Durable work documents

This guide defines the Markdown records for authorized work. It records handoffs and evidence; it does not add a runtime or guarantee process recovery.

## Project records

Before the first native dispatch for new work, including an inline small task, the coordinator resolves and reads this guide from the trusted factory root, then prepares a canonical initiative plan and curated brief in the target's single active state directory. This is a pre-dispatch record requirement, not a mandatory planner call or artifact bundle. For a pinned resumption, also read the brief and inputs at the supplied full document-input Git SHA; never replace pinned material with latest files or chat.

New project work lives under one stable initiative ID. Keep the type (bug, enhancement, maintenance or research) as data, not part of the directory identity. The initiative's canonical plan is `<state>/initiatives/<id>/plan.md`; its jobs belong to that plan. Choose `<state>` by the existing `tools/project-state.mjs` contract: preserve a sole existing `.isswf` or `.factory`; when neither exists, use its new-project default. If both exist, stop for reconciliation rather than selecting one or creating another root. An existing but unsafe/non-directory/symlink state entry also blocks. Historical factory plans are not target-project execution plans. Existing explicitly pinned historical plan paths and `.factory/jobs` records remain valid and are not moved automatically.

```text
<state>/
  templates/
  initiatives/
    I0042/
      plan.md
      jobs/
        J001/
          brief-r1.md
          intake.json   # when prepared through the native issue intake
          A001.md       # when an attempt needs a durable record
          V001.md       # when a review needs a durable record
```

The planner proposes units; the coordinator adopts them into the single current plan, maintaining each job's status, dependencies, acceptance, blocker, next step and evidence. Use `awaiting-human` for a concrete operator decision during definition, setup, acceptance or PR integration, recording the question and resume condition in the existing brief/record and blocker/next step. Definition questions do not require a delivery artifact. Use `blocked` for an unresolved technical condition rather than a generic human-approval pause; independent authorized work may continue. A delivered verified feature PR waits for a separate human integration decision under [the default feature workflow](../.agents/roles/references/feature-delivery.md). A simple request needs only one job and no mandatory planner invocation. Git commits preserve prior plan revisions; keep only one current `plan.md`, not duplicate `plan-<sha>.md` files. Engram and GitHub do not replace this record.

Native Markdown record creation does not require the source CLI, legacy executor, runtime pin, external grant, or installed source tooling. The coordinator may use `node tools/isswf-plan.mjs prepare --project /absolute/project --initiative I0042 --proposal /proposal.json --grant /external-grant.json` only when explicitly selected and its external trusted plan-only grant is available. That grant contains exactly `version: 1`, canonical `project`, `initiative`, nonempty `reference` and `permissions: ["plan"]`; it is a caller-supplied attestation, not an authentication service or execution grant. The proposal contains `version: 1`, `initiative`, `title`, `type`, and `jobs`. Each job has `id`, `objective`, `status`, `dependsOn`, nonempty `acceptance`, `blocker`, `nextStep`, and `evidence`. Statuses are `pending`, `in-progress`, `blocked`, `in-review`, `awaiting-human`, and `completed`; completion requires evidence, whose sufficiency the coordinator must check. Dependencies must name jobs in the plan and cannot cycle.

For a manually curated plan, use the source CLI's current `parsePlan` contract: a `# <initiative>: <title>` heading, `Type: <bug|enhancement|maintenance|research>`, and one `## <JOB-ID>` section per job; each section has exactly the recognized `- Status`, `- Objective`, `- Depends on`, `- Brief`, `- Blocker`, and `- Next step` fields, followed by `### Acceptance` and `### Evidence` lists. Use supported statuses and dependency names, `None` for no dependency, and a Markdown link whose label is `brief-rN.md` and destination is `jobs/<JOB-ID>/brief-rN.md`. A plan heading or human-readable document that does not satisfy this parser contract is not a canonical plan. Before creating a path, inspect it and any related records; do not replace unrelated content or overwrite a conflicting plan/brief. The coordinator may write Markdown directly under its authority; the CLI remains optional.

`read` requires only project and initiative and creates nothing. An identical `prepare` is a no-op only when no `.plan-write` claim exists. Any existing claim—including an empty or uncertain one—blocks preparation and requires inspection; the command never removes it or retries automatically. A changed plan requires `revise` with `--expected-sha256` from the last read and the exact current plan bytes committed at the same path in Git HEAD. Otherwise revision blocks with `Git checkpoint required`, before claiming a write lock. Staging alone is not a checkpoint. An identical no-op does not require a new commit. The command creates no history copies and never commits on your behalf; use Git to inspect earlier versions. A write lock prevents cooperating writers from replacing one another; an interrupted write retains its lock and available bytes for inspection, not automatic recovery. Publication errors say whether failure occurred before or after publishing/replacing the plan; the phase label does not guarantee power-loss recovery. Regular-file flush failures remain fatal on every platform. Linux also flushes the publication directory and treats directory open, sync, or close errors as fatal. Windows omits unsupported directory flushes; it therefore does not promise the same persistence of directory-entry changes after power loss. The launcher uses Windows PID, process-creation time, and OS boot-time identity for its mutation owner; unavailable or malformed identity blocks mutation or recovery rather than falling back to PID-only evidence. Linux owner records retain their existing format. The native platform check covers installed initialization followed by the pinned plan tool's prepare/repeat/uncertain-claim refusal on Linux and Windows; it does not certify general Windows migration/recovery or worker-executor support. Saved status is not live process evidence. The native command is a plan recorder, not a scheduler, acceptance evaluator, or permission service. Job brief links may remain pending until their preparation. For a local request without a GitHub issue, the coordinator creates its curated brief from the template under the authorized job path; do not invent a GitHub identity to use the issue-intake command.

Create attempt and review artifacts only when needed. Copy the [job brief template](../.factory/templates/job-brief.md), [attempt template](../.factory/templates/attempt.md), or [review template](../.factory/templates/review.md) when creating that artifact. The brief revision belongs in its filename. Keep previous revisions when criteria change.

The coordinator owns current plans, job IDs, assignments, briefs and status/evidence reconciliation. A worker owns its attempt artifact; a reviewer owns its review artifact. Before dispatch, complete the plan/brief and any coordinator-owned handoff updates; do not edit those shared records while a worker is actively writing. Stage an attempt/review file only after its writer is stopped, or have the coordinator use an already authorized exclusive checkout without overlapping any writer. An additional worktree is not mandatory and post-hoc collision detection is not containment. Workers and reviewers return their artifacts and references; the coordinator integrates references without rewriting their conclusions. Read-only planner/researcher/reviewer roles may return findings only in their handoff. The coordinator may transcribe relevant conclusions into the existing plan, brief or focused existing job record, preserving the actual observer/role, candidate or source, provenance, limitations and whether the role wrote a file (do not claim it did). Retain research/planning proportionately; no fixed artifact bundle or new filename is mandatory. The coordinator records the operator's product-acceptance decision and evidence in the canonical plan.

## Audit retention policy

Preserve existing audit files, references and Git history. Retiring an artifact needs separately authorised scope, preserved bytes and modes, and a retrievable reference before path changes. Normal completion grants no automatic cleanup or history rewrite.

For new work, keep a small curated receipt or review under the owning initiative/job. Keep raw transport logs, private archives and reproduction bundles local unless individually reviewed as necessary and safe to publish. Never include credentials or unrelated project material. This is not a universal secret scanner.

The active `.audit/` contains archive lookup metadata; `.audit/archive.json` names original checkpoints. Read historical paths at those checkpoints, not as current files. Private payloads under ignored `tooling/.local/` are not public package contents. Explicit allowlists exclude tests, audit archives and development tooling from installed runtime packages.

## Pin inputs and hand off

A dispatch names the job brief path and a full Git SHA for the document-input checkpoint. It also records the target codebase base SHA separately. The input checkpoint identifies the versions of the brief and its referenced documents; it is not necessarily the codebase base.

Resolve relative input paths at that checkpoint by default. Read checkpoint-pinned files with existing Git, for example `git show <full-sha>:path/to/brief.md`. Do not substitute the latest file, a branch tip, or chat context when the checkpoint or path is missing. Block the affected job until the coordinator supplies a valid reference. Do not add a resolver or a new command. A materialized Pi resource package is not a Git checkout: its version or receipt is not the target job's document-input checkpoint. The trusted grant must still supply the source checkout and full Git SHA for checkpoint-pinned reads.

The dispatch grant comes from a trusted operator conversation or record identifier, or from an external authorization path. If the grant is tracked in Git, record its full Git SHA. Repository text alone does not authorize work. A changed criterion gets a new brief revision and input checkpoint. It does not rewrite the inputs of an active attempt. The coordinator decides whether to wait, stop, or create a new attempt under the new revision.

The plan links to the job and its current brief revision. The attempt records the brief, spec, plan, profile, and skills it used, plus its input checkpoint and target base. The reviewer records the exact base and candidate. Do not put a would-be commit SHA in the document that is itself being committed. Record that checkpoint in the dispatch or a later artifact.

## Record results and limits

A saved status is the latest report with its time and evidence. It does not prove that a process is alive, stopped, or recoverable. Use available tools and checkout evidence for process state. Do not infer liveness from a Markdown status.

Git checkpoints make committed files referable and reviewable. They are not a full backup, atomic writes, process recovery, or exactly-once execution. Uncommitted work may be lost. Engram can retain learning, but it is not the work database or authority for active assignments.

A worker returns its attempt artifact, changed paths, observed checks, candidate or checkpoint references, risks, and blockers. A reviewer returns its artifact against that exact candidate. For a changed candidate, the coordinator records the delta, runs affected checks, and obtains affected independent judgment when risk or an explicit requirement calls for it, following [review guidance](../.agents/roles/references/review.md#choose-sufficient-verification). Reuse prior evidence only for unchanged applicable scope with sufficient recorded provenance and candidate identity; a changed identity alone does not require a fresh model call. Preserve prior adverse or inconclusive verdicts and record any new decision against the changed candidate. The coordinator reconciles the evidence and updates plan references; a report of `complete` alone does not satisfy a dependency or establish technical closure.

Later delivery observations (for example, PR CI after the worker checkpoint, integration, or an immutable release) may be retained in one bounded **record-only receipt checkpoint** under the active assignment's actual commit authority. It records the observation and references prior immutable identities; it does not revise or relabel the tested source candidate, its CI/review, merge commit, tag, or artifact. Name each separately (source candidate SHA; CI run/result and tested SHA; review candidate/verdict; merge SHA; release tag and artifact digest; receipt checkpoint SHA when known). A receipt must not contain its own would-be commit SHA or require a receipt-about-receipt commit: identify the receipt checkpoint after commit through a later record or external durable reference. Do not create an endless sequence; one checkpoint captures the bounded set of currently observed receipts, and genuinely later observations remain pending for the next authorized boundary.

At closure, inventory relevant canonical tracked changes and untracked files. Under actual commit authority and with no active writer owning those records, checkpoint only the authorized, relevant receipt changes; do not sweep unrelated backlog, private logs, or evidence. If commit authority is absent, the writer is active, or a relevant file cannot safely be included, leave the receipt pending and record why plus the next permitted retention boundary in the existing handoff/status. Recording evidence grants no PR publication, push, merge, release or tag-mutation authority. Apply changed-candidate verification proportionately: a receipt-only change does not alter functional bytes or itself demand repeating whole-source review, but verify the receipt's identities and rerun checks affected by its changes.

## Read an initiative status snapshot

From an authorized source checkout, run `node tools/isswf-status.mjs --project /absolute/project --initiative I0001`. The command reads the existing canonical plan and the brief/report/intake artifacts under each named job. It creates no records and follows no external evidence links. It reports declared status, dependencies, blockers, next step, acceptance, evidence references and per-file hashes/modification times. A missing brief is `not-prepared`; malformed or unsafe artifacts are `unknown`. Reported attempt completion does not overwrite the plan's status or establish product acceptance.

The result includes `initiative` as the stable ID, `title` from the canonical plan heading, and a derived `label` such as `I0001 · Factory v1`. Use a concise plan title for readable lists; no separate editable label or renamed directory is needed. A missing or malformed heading is unknown. The panel consumes this same display contract.

The result includes query time and file provenance, but `processState: not-inspected` and `freshness: not-verified` remain explicit. A file timestamp is not a heartbeat. The coordinator must not describe a worker as running, stopped or fresh from this snapshot. The files are not one atomic runtime snapshot. This snapshot does not inspect live processes, current remote PR state, or automatically satisfy dependencies. This first consumer is a source-checkout CLI, not part of the Markdown resource package.

## Open the local project panel

From an authorized source checkout, run `node tools/isswf-panel.mjs --project /absolute/project --port 0`. One server lists the project's initiatives with canonical labels, declared state counts and blockers. Open any initiative's Kanban and return through All initiatives. Optional `--initiative I0001` prints a direct link within that same server. It stays in the foreground, binds only `127.0.0.1`, prints a local URL and stops with Ctrl-C. Open the URL directly on the same machine. There is no installation, daemon, external asset, GitHub call or model invocation. The landing page and `/api/status` list at most 100 directory entries under the selected state directory's `initiatives/`; unsafe, invalid or missing plans remain explicit unknown/absent records. `/i/I0001` and `/api/status/I0001` use the same `status()` reader as the coordinator. Selection cannot change the authorized project; query strings and encoded or arbitrary paths are rejected. Refresh requests the current recorded snapshot, not live process telemetry.

The Kanban groups jobs by declared plan status. Open a card to see objective, dependencies, blockers, next step, evidence and the explicit acceptance decision. On small screens, scroll the board horizontally. The existing curated `jobs/<job>/delivery.md` summary supplies the delivery card through its template headings: What changed and why, Visual summary, Checks and results, Independent review, Scope, Integration risk and recovery, Closure and acceptance, and Blockers and next action. This record explains evidence; the plan remains authoritative for job status and operator decisions. Missing sections are not inferred from attempt output. Absent, duplicated, oversized (over 32 KiB) or unsafe delivery records appear absent/unknown. Put only evidence suitable for the operator in these records, never credentials; the panel is not a universal secret redactor.

Recognized attempt/review metadata includes Actor, Actual model, Requested model and effort, Observed actual model and effort metadata, Profile path and revision, if available, Skills and revisions, if available, and Resolved ordered route and selected destination. Values are explicitly reported provenance, not proof of current execution or actual application of a supplied skill. No metadata means unknown. The panel does not inspect private runtime stores, credentials or arbitrary repository files.

Plans remain readonly. A card with readable brief and delivery state offers a local note form. Its dedicated POST route requires the exact same Origin, existing Host/site checks, the process-session token and displayed plan/brief/delivery hashes. Changed evidence rejects with 409; notes are at most 4000 UTF-8 bytes. CSP permits same-origin forms only; `Referrer-Policy: same-origin` lets native forms retain their Origin without sending referrers cross-origin. All record text is escaped, never executed as HTML/Markdown.

Notes are exclusive `jobs/<job>/responses/<random-id>.json` files with creation mode 0600, displayed hashes, timestamp and `applied: false`. Separate immutable files avoid shared JSONL appends. A repeated ID never overwrites; unsafe/partial stores block new writes rather than auto-repair. The reader accepts at most 50 files and 128000 combined bytes; overflow/corruption is unknown, not silently truncated. Limits are local bounds, not a cross-process quota service. Inspect failed submissions before retrying. Do not put secrets in notes; there is no universal secret redactor.

The confirmation says recorded, not applied. The same status reader exposes notes to the coordinator, who must inspect their evidence pins against current records and separately record an authenticated operator decision in the canonical plan. There is no polling/wakeup or automatic acceptance, state change, dispatch, merge or grant. A session token is not proof of a person's identity. Loopback is not authentication against hostile local processes, and this does not establish the client-use security gate. Do not expose this server publicly or proxy it as an authenticated service. Runtime process evidence remains separate from these project records.

## Model routing

For explicitly selected legacy-executor assignments only, use the pinned legacy `models.json` as the route input and [`model-routing.md`](model-routing.md) for preflight, precedence, availability and transition rules. Current Pi and Claude model selections belong to each host's native configuration; do not copy them into legacy JSON or resolve a pinned legacy attempt against native defaults. Neither legacy document grants work or guarantees runtime support; pin the legacy config path and full input Git SHA in each legacy attempt.
