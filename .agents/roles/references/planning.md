# Planning guidance

Use this reference when the coordinator asks for a plan proposal. The proposal is a decision aid, not an authorization or an update to the canonical plan.

## Build the proposal

1. Confirm the trusted grant, complete brief in the host handoff or an existing document, target base and permitted effects. An ordinary handoff does not require a committed brief or document-input checkpoint. For explicitly checkpoint-pinned document assignments, also require the committed brief path and full Git SHA of its document-input checkpoint, separately from the target base. Resolve those inputs using available Git or coordinator-supplied readable checkpoint material identified by original paths, full SHA and coordinator-verified provenance. A missing or abbreviated required checkpoint or unavailable pinned input blocks planning; never substitute the latest files. Read only the relevant local grounding and reopen current source paths before relying on them.
2. State the user-visible outcome, why it matters, included scope, exclusions, and acceptance evidence. Separate observed facts from assumptions and unresolved decisions.
3. Match the plan's detail to the work. A clear single outcome may need one concise unit. When only a person can resolve product meaning, scope, acceptance or a missing setup choice, name the question and recommend `awaiting-human` for that affected work, even before implementation. A technical fact belongs in grounding and verification, not in a generic approval request. Preserve the brief's full delivery boundary rather than inserting approvals between already covered steps.
4. For multi-unit work, order vertical functional units so each has a demonstrable outcome, bounded scope, acceptance, relevant verification, dependencies, and a coherent commit/checkpoint. Do not invent line quotas or divide user value into frontend, backend, or storage phases. A mechanical change may use coherent mechanical units when vertical slices do not fit.
5. Give every dependency a concrete unblock condition. For code dependencies, name the contract and require its integration before dependent work starts unless the grant explicitly authorizes another local route. Do not treat a proposal, review pass, or unintegrated change as an integrated contract.
6. Include implementation verification, independent review when required, corrections, and re-verification of affected checks and review after changes. Select checks by behavior and risk. Do not prescribe an interview or TDD unless the unresolved decision or task makes it useful.
7. If stacking PRs is useful, present it as an optional local delivery proposal with each base, dependency, and ancestor-change recheck. State that it grants no remote permission.
8. Return a separately labeled plan proposal through the coordinator's authorized return channel; write an artifact only when explicitly authorized. Without artifact-write permission, return it in the host response for the coordinator to persist. Identify any assigned pinned inputs and the target base. Leave the canonical plan unchanged.

## Stop conditions

Return a focused blocker when the grant, complete brief, authorized checkout, required acceptance or a necessary product decision is missing. For explicitly checkpoint-pinned document assignments, a missing committed brief path, abbreviated or missing required full Git SHA, or unavailable pinned material also blocks planning; never resolve assigned pinned inputs from latest files. Do not broaden scope, authorize a worker, invent durable records or infer remote permission from a delivery proposal.
