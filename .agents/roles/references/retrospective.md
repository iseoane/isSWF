# Retrospective procedure

## Scope and evidence

For a completed feature or bug, review the full authorized work for that job, even when it had no incident. For an explicit session close, review authorized project work since the previous retrospective, including completed work and active or pending jobs. A chat ending alone does not trigger this review.

Use only project-owned artifacts and records covered by the grant, such as the approved brief and pinned inputs, attempt and review reports, decisions, checks, changes, and outcomes. Read an instruction source before proposing a change to it. Do not search broad session logs, other clients' records, or unrelated project history. Engram may hold external learning, but it is not job authority, current job state, or evidence that an action occurred. Check any relevant memory against authorized project evidence.

Record failures, decisions, friction, and outcomes with the source that supports each claim. Separate observed facts, inference, and unknowns. If the evidence is missing, inaccessible, or outside the grant, say so rather than filling gaps.

## Session close with active work

Record each job's last known state and the evidence and time that support it. Mark liveness or completion unknown unless directly verified through an authorized live source. Do not stop, restart, replace, or otherwise affect active workers. Do not rewrite pinned briefs or their inputs. Session close is an analysis boundary, not a lifecycle command.

## Find useful changes

For each proposed improvement, state the observed problem, evidence, impact, affected project or factory process, proposed destination, and a check that would show whether the change helps. Separate a project-specific fix from an improvement to the factory process. State whether it fits the current grant or needs a new grant; never infer permission from the retrospective.

Before proposing a change to `AGENTS.md` or a skill, inspect the actual current source and identify the exact rule or gap. Prefer a structural correction, such as a type, check, or other deterministic mechanism, when it can prevent a mechanical failure. Do not repeat an instruction that an existing source already expresses. Reserve instructions for judgment that cannot be encoded reliably. Do not edit policy automatically. Any policy change needs a separately authorized change, risk review, verification, and the project's normal review process.

Check known local proposals and issue records in the authorized project artifacts for duplicates. Do not query a tracker or create/update an actual issue unless the grant explicitly authorizes that action. A factory improvement issue may be drafted locally for later triage. Label it `DRAFT`; it is not an issue, authorization, or executable job.

Do not convert one preference or isolated event into a general rule without evidence. Preserve rejected and deferred proposals with their reason when needed to prevent repeated work. An empty finding is valid when the review found no supported improvement.

## Return

Use `.factory/templates/retrospective.md`. Identify the reviewed interval or completed job, evidence inspected, findings, proposals, duplicate check, limits, and next action. For a session review, list pending jobs without treating their status as live or complete. If analysis fails, record what failed and leave the retrospective pending. This pending analysis does not block a delivery already verified on its own merits.
