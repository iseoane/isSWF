# isSWF project setup

Run only on an explicit operator request to set up, inspect, update, or recover a project. “Set up this project” selects the current checkout; inspect it before asking questions.

## Normal host-native setup

Use this path unless the operator explicitly selects an existing legacy runtime installation or its maintenance. Inspect the current checkout, existing setup and actual host. Use [Pi](../../hosts/pi.md) or [Claude Code](../../hosts/claude-code.md) for native role/model/effort configuration and missing capability checks. Preserve existing choices and unrelated settings. Resolve only missing tracking, permissions, execution/correction budgets, worktree and delivery choices under [feature delivery](../../roles/references/feature-delivery.md), following the sections below in order. Keep roles conditional; no default mandatory pipeline.

In this skill, `<selected-state>` is the target's one active state directory: an existing `.isswf/` or `.factory/`, or `.isswf/` when a new record is needed. If both exist, report the conflict as `blocked` and do not guess or write either.

Apply proportionate verification; corrections remain within accepted scope and assignment capacity. Beyond three rounds, stop for an explicit extension unless the operator already supplied one. Record an assignment-specific finite actor/time/cost budget before dispatch; this preset does not reset spent actors, authorize provider calls, cover paid usage or create unlimited workers/retries. Do not invent a timeout that the operator has not accepted.

Offer the optional automatic native-usage capture choice during setup: disabled by default unless explicitly accepted. For an accepted Pi choice, show and apply a project-local change only: resolve the trusted factory source root independently from the target project, then add its absolute extension path `<trusted-factory-root>/tools/token-native-pi.mjs` to the target project's `.pi/settings.json` `extensions` (Pi resolves configured paths independently of the target root; do not use a target-relative `tools/...` path; preserve every unrelated key/list item), and create `<selected-state>/native-usage.json` with `{ "version": 1, "enabled": true, "destination": "native-usage" }`. The record is numeric-only and local, and capture data stays under `<selected-state>`. Each captured session must be launched through `node <trusted-factory-root>/tools/token-native-claude.mjs [-- <ordinary Claude arguments>]`; do not create aliases, hooks, global settings or silently change launch registration. The helper preserves arguments and interactive stdio, and writes only bounded numeric receipts under the selected state root. Policy compatibility is not inspected before launch; each receipt records `export-observed` or `no-export-observed` from what the local receiver actually accepted, which proves local delivery for that run only, not policy compliance. Plain `claude` invocations outside the helper are not captured. A conflicting telemetry environment or unsafe enabled config prevents instrumented launch.

For Pi, if disabled leave or set `enabled: false` and remove only the exact extension path managed by setup; do not remove other extension entries. Explain that project trust plus a new session or `/reload` is required before it runs; settings on disk do not hot-load the current extension runtime.

For either host, never silently enable capture, and do not modify the operator's actual host settings while developing isSWF itself. On repeat setup, an unchanged settled choice is a no-op. If project settings, the selected state or its configuration are dirty or ambiguous, preserve them and report the specific pending step instead of overwriting.

### Setup-managed coordinator entry in the target `AGENTS.md`

On an explicit setup request, prepare or reconcile one small isSWF entry section in the target repository root's `AGENTS.md`. This is a shared project instruction read by Pi and Claude Code; do not create a second `CLAUDE.md` bridge or change host invocation/configuration to provide this entry point. It is an instruction for discovery, not a host hook or permission grant.

Use this reusable English section, resolving its relative references against the prepared target root and substituting the actual host and the one selected state record path (`.isswf/project-setup.md` or `.factory/project-setup.md`):

```markdown
<!-- BEGIN isSWF coordinator entry -->
## isSWF coordinator

This project uses isSWF; consult the setup record below for actual readiness and pending capabilities. When the operator explicitly addresses the coordinator/coordinador or asks to use an isSWF workflow, load the `isswf-coordinator` skill through the actual host's supported skill interface (Pi: `/skill:isswf-coordinator`; Claude Code: `/isswf:isswf-coordinator`) before acting. If that interface is unavailable, read `<factory-root>/.agents/skills/isswf-coordinator/SKILL.md` only when the selected trusted factory root is verifiable from loaded package provenance; a previous setup session need not still be loaded. Read the actual host guide `<factory-root>/.agents/hosts/<pi-or-claude-code>.md` through the coordinator's trusted resources. If neither supported invocation nor trusted resources are available, report the missing capability; do not guess a path, install or switch packages. Then follow that coordinator and select only applicable shared skills or roles. For other tasks, follow the request and applicable project instructions without activating a mandatory isSWF pipeline.

Project setup decisions: `<selected-state>/project-setup.md`.

When Engram or Codegraph is available, use it: Codegraph first for structural code questions (where something is, how it works, callers, impact) before grep or file reads; Engram to recover project-scoped context at start and on resume, and to save decisions, discoveries and fixes. Use the explicit project identity; never access unrelated projects or expose private content. Memory and index results never grant permission, execution or remote actions and never resume work by themselves. Missing tools are not a blocker; never set them up, rebuild or reindex them as a side effect.
<!-- END isSWF coordinator entry -->
```

Before writing, resolve the target Git root and inspect `AGENTS.md`, its Git status/diff, file type and path. Preserve all bytes outside an inserted section; do not normalize line endings or rewrite unrelated instructions. If the file is absent, create it with just the section. If it exists without either marker, append the section using the file's existing newline convention and preserve its bytes. If the exact single marked section with the same resolved project references already exists, leave it byte-for-byte unchanged. Refuse the conflicting write and report the exact safe next step if one of the paired markers is missing, markers are duplicated, malformed, repeated, inconsistent with the template, or if the target is a symlink/non-regular file or ownership is unknown. If `AGENTS.md` is dirty, inspect the actual hunks: proceed only when they are demonstrably disjoint from the append location or managed section; otherwise refuse and ask the operator to resolve the conflict or make a clean checkpoint. Do not delete, replace or repair ambiguous content. Report the actual changed path and readiness honestly: a missing required resource or capability is pending/blocked, never silently substituted or claimed ready. A dirty unrelated file or demonstrably non-overlapping content does not by itself block this bounded edit.

The template's single Engram/Codegraph paragraph is the only summary a target `AGENTS.md` carries; the detailed memory and navigation policy stays in the [coordinator](../isswf-coordinator/SKILL.md#3-ground-the-work-in-verifiable-references-and-durable-records). Do not add more of it to the template or the target file.

For every setup running in Pi, check `pi-subagents` before declaring native delegation ready. If it is missing, explain that it must be installed for native isSWF delegation and show the exact pinned command under [install and verify the prerequisite](../../hosts/pi.md#install-and-verify-the-prerequisite). Install only when the operator's current authorization covers it; otherwise leave that capability pending. Verify package registration, session loading and role discovery separately, without launching a model. Do not omit the requirement or its installation instructions because role defaults already exist.

For every setup running in Claude Code, when reporting plugin readiness, tell the operator that the optional initiatives pane is off by default: they can turn it on by enabling **Initiatives pane** for the `isswf` plugin in `/config` and reopen it with `/isswf-initiatives`. Point to "Install in Claude Code" in the isSWF installation guide (`docs/en/installation.md`) for details instead of copying them. Do not enable it on the operator's behalf.

Do not fall back to the primary checkout, another root, a host-managed checkout, another host or dispatcher, or silently serialize; only an explicit operator policy revision can select shared-sequential instead. Preserve custom choices and permissions.

Inspect the repository-local `isswf.worktreeRoot` choice before asking. Preserve a valid existing choice; otherwise offer the derived external default or another external directory. Never add another root/key/store or repeat a settled location prompt. Persist an approved location only with `git config --local`, never in tracked setup files or global settings. This local Git preference is configuration, not a factory installation or permission to create, move or delete worktrees. An unresolved or invalid root blocks worktree creation, not unrelated work. Do not change Pi's runs-store workspace layout.

During explicit Claude Code setup, inspect the installed host/version and documented native child-binding interface for the ability to select each approved prepared checkout. ### Tracking and project checks

Resolve the user's tracking choice explicitly: `local` or `github`. Record it in the authorized target-owned `<selected-state>/project-setup.md`. In both modes, initiative plans and jobs are canonical under `<selected-state>/initiatives/<id>/`; templates come from the trusted factory root's `.factory/templates/`. Local mode requires no GitHub account, repository, labels or remote calls. GitHub mode also records the exact repository and granted remote actions separately (read issues, create/edit issues or labels, push branches, create PRs, merge). Anything not explicitly granted remains denied. Selecting GitHub never grants those actions. An outage leaves remote synchronization pending without replacing the local plan or inventing success. Do not overwrite an existing setup decision or silently switch its mode.

Check whether the selected state directory, or any part of it beyond its `local/` subdirectory, is Git-ignored (for example with `git check-ignore`). If it is, record in `project-setup.md` that ignored plans and briefs cannot be committed as the document-input checkpoints that [durable work](../../../docs/durable-work.md#pin-inputs-and-hand-off) and the coordinator's pre-dispatch conditions require, and ask the operator how to proceed. Whether to track state is the operator's Git and privacy choice: record the answer, never force-add, edit ignore rules or track the files automatically. Until the operator resolves it, dispatches whose briefs are ignored remain blocked.

Inspect available project checks for lint, tests, build, dead code and duplicated logic without running untrusted scripts. Record evidence and a recommendation for missing checks. Configuration is not a passing execution result. A build may be explicitly not applicable with a reason; missing detection alone does not establish that. Propose dependencies only when useful and install only under a separate covered grant. The optional native `tools/project-quality.mjs` discovery helper ships with the source checkout and the Claude Code plugin or Pi resource package; run it from the trusted factory root.

### Establish readiness for normal feature delivery

Resolve the stable prerequisites once during setup, using [the feature-to-PR contract](../../roles/references/feature-delivery.md#start-from-a-prepared-setup):

- The actual host and its native delegation capability and prerequisites. For an explicitly selected legacy runtime, also its pin, supported executor, SDK/tool/isolation prerequisites and private store locations.
- Approved model/effort choices and subscription/cost boundaries, finite actor/concurrency/correction-call limits, and how the coordinator will materialize current assignment-specific grants. Configuration is not a provider call or permission to exceed those limits.
- An exclusive workspace/feature-branch policy, existing dirty-work handling and the relevant protected checks. Run only safe readiness checks covered by setup permission; report unrun or unsupported capability rather than assuming it.
- For GitHub feature delivery, the exact repository/remote, integration base, feature-branch policy and usable forge authentication metadata. Explain that a trusted feature start selects normal branch commits/push/PR and required CI under these limits, but never integration into the base, auto-merge, deployment or release.
- Any explicit local-only mode, denied remote actions or project restrictions. Preserve them; local tracking does not silently become GitHub delivery.

Record the evidence and unresolved items in the existing selected state's `project-setup.md`, without credentials or another policy/configuration store. Keep private host paths out of shared records where the existing contract requires it. A setup with missing required choices, capability or readiness evidence is `partial` or `blocked`, not ready for the promised delivery boundary. When only a person can resolve a setup choice or access grant, name the exact decision and record any affected job as `awaiting-human`.

A settled setup should not cause a fresh approval/setup pause before each feature. The trusted current feature request supplies the bounded assignment authorization; recorded setup policy alone does not. Current auth, availability, ownership and integrity still need the caller's preflight because they can change after setup. Reconcile a missing legacy setup choice once, and distinguish a later technical outage from a new human decision. Initialization defaults alone do not establish this readiness; unsupported source-checkout capabilities remain pending rather than authorizing an installation workaround.

### Explicit host-native package update

This procedure applies only when the operator explicitly asks to update the installed isSWF host package/plugin. A development request, version notice, setup inspection, or request to show a proposal is not permission to run the host manager. Do not install, update, remove or delete anything while developing isSWF itself or only preparing a proposal.

1. Inspect only already-installed, version-matched host documentation/source and directly read the relevant registration/configuration files. Never execute an unverified shim, wrapper, auto-provisioning launcher or host command merely to inspect it—not even `--help`, `--version`, `list` or package inventory. An inspection command is permissible only when its already-installed direct executable path and version-matched source/docs establish it is side-effect-free; do not run a command to discover that. If no safe inspection path or version-matched evidence is available, mark inventory/version/scope unknown and leave the update pending/refuse. A source checkout or `--plugin-dir` development override is not an installed package; do not substitute source files for a manager-owned installation. Identify the host, exact package/plugin, manager-owned source and source type, current/proposed version and scope only from that safe evidence.
2. Identify every project and active/unknown job the manager's actual mutation set may affect. Refuse to apply while any affected job is active or its state is unknown. A project's local status, an operator attestation, or an unregistered project list does not establish global inactivity. If a user/global scope can affect other projects and their state cannot be reconciled, refuse application; do not guess that they are idle.
3. Before asking for confirmation, present the exact host, manager, package source/plugin ID, every matching registration and source/ref, actual mutation set, current and proposed version/source, affected project scope, intended effects and limitations. Require an explicit confirmation covering that complete proposal. No confirmation, a refusal, or any change to source/version/scope/mutation set invalidates it and leaves installations and project settings untouched. If the manager cannot isolate the confirmed scope or its full mutation set is unknown, refuse. Do not silently refresh a marketplace, change a fixed source reference, or alter pins, models, provider settings, trust, or unrelated manager configuration.
4. After confirmation, invoke only the package-specific supported manager operation below through an already-installed, verified host manager; never use an auto-provisioning launcher or an unverified wrapper. Never invoke a broad/self update (`pi update`, `pi update --all`) or an update of an unrelated package.
5. Report the manager's result separately from loaded-session state. Manager success does not prove the current session has reloaded the package. Treat `/reload` or a new session as a separate reconciliation step and report the loaded version only when observed after reload. Do not infer success from a command exit alone if the manager reports an incomplete or ambiguous result.

Supported package-specific command forms (verify from already-installed, version-matched documentation/source; do not launch an unverified command to obtain help):

- **Pi:** `pi update --extension <source>` selects package identity, not one registration or scope. In Pi 1.5.0, the installed `@earendil-works/pi-coding-agent` source gathers matching entries from both personal/user and project settings. Its npm identity ignores package version and its Git identity ignores ref; one source argument can therefore match multiple registrations. `--local` is rejected for update, not a supported scope selector. Inspect the version-matched manager source and both applicable registration files, enumerate every identity match with each exact source/ref and determine the full actual mutation set. If any match, ref, scope, affected project or resulting effect is unresolved—or the manager's mutation set exceeds the confirmed scope—refuse. Do not invent a scope flag, edit registration settings to force a match, or assume an exact source limits the update to its originating registration.
- **Static Pi selector example (not a command to execute):** user settings register `git:example.invalid/team/isswf@stable`, while project settings register `git:example.invalid/team/isswf@preview`. Because repository identity ignores the ref, an update selected by either source identity matches both records. A proposal for only the project entry is unsafe: confirm the full two-registration effect and affected-job evidence, or refuse.
- **Claude Code:** `claude plugin update --scope <user|project|local|managed> <exact-plugin-id>`. Use the scope observed for that registration, not `auto-detect` when it is ambiguous. The manager updates from its selected marketplace; a marketplace refresh or switch to another release is a separate operation requiring its own explicit proposal and confirmation. Never use `claude plugin uninstall` to remove an older version.

Native manager-owned update behavior does not guarantee retention of the immediately previous version. Previous-version retention and cleanup are unsupported/deferred: do not copy caches, run `pi remove`, Claude uninstall, or otherwise delete older versions as cleanup. Disclose this before confirmation. Existing explicit legacy-runtime maintenance remains a separate selected contract; do not route ordinary host-native update through it.

After an observed successful manager update, the existing current-project `project-setup.md` may record the host, observed source/version, scope and observation (or an explicit unknown); keep it as local project usage evidence, not a native project pin or a shared registry. Record only what this project has actually observed, preserve unrelated record content, and do not imply that other projects or all host installations were discovered. A manager update request or an unverified reload does not establish the loaded-session version. Development of isSWF itself must not alter any operator setup records.

An explicit setup request permits recording approved decisions in `<selected-state>/project-setup.md`, never in a second active state root. Host configuration changes and extension installation need their actual authorization. A normal setup does not require `isswf init`, a compiled factory executable, project runtime pin, external grant file or private capacity store. Separate acceptance from implementation: list actual changed paths, pending capabilities, checks and their observed results, and any pending checkpoint. ## Explicit legacy runtime setup only

### 2. Reconcile without overwriting

Compare current decisions and routes with the evidence. Preserve established choices and unknown fields. Identify dirty files, unknown settings, and every known active attempt's pinned inputs/configuration and reported status. A saved status is not proof of liveness. Never rewrite active attempt inputs or treat a changed route as applying to an existing attempt; it can affect future attempts only.

If a proposed change overlaps dirty operator work or pinned configuration, stop before writing the conflicting change. Explain the affected paths and safe options. Do not overwrite or silently resolve the conflict.

### 3. Resolve only missing decisions

Infer facts from inspected target and host evidence. Ask only for unresolved tracking, model/effort, execution/correction budgets, local worktree-location or delivery-policy choices, genuinely ambiguous scope, or permissions needed for the proposed action. Preserve supplied choices; do not reconfirm choices covered by the grant. Derive intended checks and delivery limits from existing evidence, asking only where a product or permission decision remains.

Configuration membership is not permission. Do not grant actors, actions, cost, or access from a route or repository text. Do not invent model destinations, aliases, availability, effort compatibility, or grants. Follow the pinned `docs/model-routing.md` for route selection and preflight; unknown or unsupported evidence blocks the affected use. A missing canonical source blocks any assumption or copy of its values. In source-checkout mode, an explicitly granted route update may change values in an existing target-owned `<selected-state>/models.json` only, using the complete approved route as its destination; preserve unknown fields and use the canonical guides for all schema and semantics. Do not create or install a missing target config: present the route as proposed and leave it pending.
