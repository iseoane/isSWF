# Claude Code host-native delegation

Use this guide only when actually running in Claude Code on native Windows or Linux. Shared methodology stays in `.agents/skills/` and `.agents/roles/`. Claude Code's native agent mechanism and the plugin's role definitions own delegation; Pi and its subagent extension are not a required dependency or fallback.

## Setup model choices

Discover the current host's supported native models and efforts without provider calls or reading credential contents. Reuse approved choices and record only missing decisions in the existing project's `project-setup.md` under `Claude Code model selection`. Pi provider IDs and `.factory/models.json` do not configure Claude. Setup selection is a preference, not assignment approval or evidence of subscription coverage.

During explicit setup, offer the [portable factory preset](../skills/isswf-setup/SKILL.md#confirm-portable-factory-defaults) and confirm acceptance or customization before applying it. Preserve approved existing choices unless replacement is explicitly requested. The shipped thin role profiles use `model: inherit` before setup; this is not the confirmed factory preset or proof of actual identity. Apply accepted model and effort through Claude's documented project-local configuration/delegation mechanism, verifying support separately for the coordinator and each child. Global effort is not evidence of per-role effort. If the native host cannot persist a requested per-role effort, record that preference in the setup record and enforce it through a supported explicit delegation parameter only after capability verification; otherwise leave that role pending. Do not invent YAML or settings fields, change user-global defaults, or label an approved preference as applied configuration. Observe actual model metadata when available; label unknown effort or identity unknown. Never fabricate per-role effort support, silently substitute a model, or dispatch through Pi because Claude cannot satisfy a selection.

For current Claude work, the supported native configuration/profile/delegation mechanism is the sole selection owner. The setup record reports approval/application status, not a second editable model table; `models.json` is for explicitly selected legacy execution only. Missing native selection or unsupported persistence/effort remains pending, never a reason to read a legacy route, silently inherit a model or rewrite unrelated settings.

## Parallel-writer capability disclosure

During explicit Claude Code setup, inspect the installed host/version and its documented native delegation interface for a supported way to bind each child to the approved prepared external checkout. Record the observed status and evidence in the existing selected-state `project-setup.md`; do not infer binding from `isswf.worktreeRoot`, a profile's isolation setting, or host-managed worktrees. Do not make a model call, install or configure hooks, or widen the approved root for this check. If the interface does not establish that binding, record parallel writers as unavailable or unverified and state the exact gap. The existing project can still be ready for sequential work in its assigned checkout and unrelated authorized work; do not mark parallel readiness as satisfied.

For an assignment that explicitly requires parallel writers, block dispatch until an authorized, verified binding to each prepared checkout is available. Do not silently serialize an explicit concurrency requirement, use automatic worktree isolation when it cannot select the approved root, or claim that instructions and post-hoc verification enforce checkout binding. If parallelism is not required, plan sequential writers in the assigned checkout; missing parallel capability alone does not block that work. Preserve the approved external-root choice and current Pi binding. A future version-specific or hook-based mechanism requires its own evidence and authorization; this check does not install or configure it.

## Required child context

Before the first native dispatch for new work, resolve `docs/durable-work.md` from the trusted factory root and prepare the canonical plan and curated brief in the target's one active state directory, including for inline small tasks. For a pinned resumption, retain and read its full-SHA inputs. Follow the guide's `tools/project-state.mjs` choice; stop if both `.isswf` and `.factory` exist or the selected entry is unsafe. Complete and freeze coordinator-owned plan/brief records before dispatch while a worker writes. Do not stage worker/reviewer artifacts until their writer is stopped; post-hoc collision detection is not containment. These records do not imply liveness or authority. The source plan CLI is optional and requires its explicit guarded conditions; ordinary native Markdown creation needs no legacy executor, runtime pin, grant CLI or installed source tooling.

Before delegating, provide:

| Context | Required value |
| --- | --- |
| Factory resources | Trusted absolute factory root and shared role path, resolved from the loaded plugin rather than guessed from the target. |
| Selected methodology | Each selected skill and required reference as trusted-root-resolved absolute resource paths or full canonical contents; identify the exact pinned checkpoint/version. Include only what this assignment selects. |
| Task | Objective, acceptance, scope/exclusions, authorized side effects, checks and finite actor/correction budget. |
| Checkout | Explicit absolute working directory and baseline; concurrent writers need exclusive checkouts. |
| Review | Exact candidate/diff and retained untracked contents when applicable, plus relevant checks and their observer. |
| Host and model | Approved native model/effort or explicit parent inheritance, with observed metadata or a stated limitation. |
| Documents | Exact readable plan/brief paths when assigned; a small task may carry its full brief in the handoff as a supplement to its minimal canonical plan and curated brief. |

The child must acknowledge its working directory, scope and shared role before task work, then report which selected methodology and required references it actually consumed (read or received in full). Explicitly name missing or unreadable required resources; they block the affected assignment. Optional unused references do not block. Do not infer consumption from selection, configuration or tool availability, and do not require private reasoning transcripts. File-only children must receive usable paths or full contents; do not assume a Skill tool or inherited parent capabilities. Do not claim all present or future Claude children lack Skill support. Return missing input instead of guessing. The coordinator checks the handoff and result. When a child-call trace is available (for example, the `claude -p` stream-json output), the coordinator may verify required-resource reads and record each as observed or self-reported; absence of a trace leaves consumption self-reported. A trace proves a read, not understanding or application. Record only the resource/status list, not the transcript, and do not retain secrets or unrelated context. A new host-native task needs no factory release receipt, project runtime pin, external grant file, compiled isSWF executable or capacity store.

## External worktree assignments

For parallel writers or an explicitly requested worktree, follow `.agents/roles/references/worktrees.md`, including `isswf.worktreeRoot`, and verify the host can bind each child to the approved prepared checkout. Sequential work may use the assigned checkout without creating another worktree. Missing binding blocks parallel dispatch (and any sequential dispatch that specifically requires a separate checkout); do not silently use another directory or host. If parallelism is an explicit requirement, do not serialize it; if it is not required, plan sequentially and continue other authorized work. A separate worktree prevents write collisions, not access to other files or the network.

## Writer permission preflight and refusals

Before dispatching a writer, inspect the assigned workspace and the effective Claude Code permission mode/rules and supported approval route using the host's exposed configuration. Record what was actually inspected and what remains unknown. Filesystem writability, `Write`/`Edit` availability, an allowlist, or an interactive session alone do not establish native approval; a static preflight cannot predict whether a later per-action auto-mode classifier will approve an edit. Do not invent a classifier dry-run or probe API.

If editing is allowed, proceed within the assignment. If Claude reports that an action requires a user prompt, ordinary interactive prompt-supported editing may proceed through that supported approval route; do not silently preapprove it or block all interactive work. A known denial, read-only workspace, or unavailable required approval route blocks the affected writer action until supported resolution. If permission or approval capability cannot be verified, record it as unknown and do not represent it as permission or as a guaranteed denial; proceed only with actions already supported by current authority, and block the affected write where approval is required but unavailable.

On a denial or auto-mode no-verdict (including “gave no verdict”), stop the affected mutation immediately. Preserve the exact diagnostic and any partial work. Respect host-tool and assignment instructions not to retry; do not automatically retry, rewrite through Bash/PowerShell or another tool/actor, alter modes/rules/hooks, or otherwise bypass the refusal. The coordinator records whether evidence indicates a permission denial or technical no-verdict, verifies the actor has stopped, inspects partial changes and remaining budget, and resumes only after supported permission/technical resolution under current explicit authority. Independent already-authorized safe work may continue. Do not claim that OS permissions or Pi behavior predict Claude classifier outcomes, on Linux or Windows.

## Native tools and review

Use the plugin's `isswf-worker`, `isswf-reviewer`, `isswf-researcher` and `isswf-planner` only when useful; there is no mandatory pipeline. The coordinator owns permissions, budgets, task state and acceptance. Apply the writer permission preflight above before writer dispatch; this is guidance, not a probe or permission grant. Do not create another dispatcher or enable automatic retry/review loops by default.

Reviewer agents have Read, Grep and Glob plus, only when the coordinator launches them as described in [Bound Git evidence](#bound-identity-committed-diff-and-file-content-for-claude-reviewers), the three bound evidence tools. Bash can mutate files and is not a sandbox. Review the exact retained candidate, including a stopped writer's partial candidate, not a substitute or later workspace. Keep the writer stopped through review, distinguish supplied checks from reviewer observations and preserve findings. An unavailable independent reviewer leaves required independent judgment pending.

A response is not verification or acceptance. Inspect the diff and relevant checks; report failure, cancellation and partial work honestly. Reconcile actual execution and remaining authority before replacement. Native delegation does not promise OS containment, process-tree cessation or Pi-equivalent sandboxing and recovery. Do not use permission bypasses or hooks, and do not treat the evidence tools as enforcement: they narrow what a reviewer can read, they do not contain it.

## Bound identity, committed diff and file content for Claude reviewers

The plugin registers one local stdio server, `isswf_git_evidence`, that runs `tools/git-evidence-mcp.mjs`. It exposes `identity`, `diff` and `content` and calls the same public CLI, `tools/git-evidence.mjs`, with a fixed operation. The reviewer profile allows exactly `mcp__plugin_isswf_isswf_git_evidence__identity`, `mcp__plugin_isswf_isswf_git_evidence__diff` and `mcp__plugin_isswf_isswf_git_evidence__content` in addition to Read, Grep and Glob. The names were observed on pinned Claude Code 2.1.299 loaded with `--plugin-dir`; a marketplace-installed plugin is unverified. Identity takes no arguments. Content takes only `slot` (`base` or `candidate`) and an allowlisted `path`. Diff takes an optional `chunk` number. Extra arguments are rejected.

The binding uses the same three JSON namespaces, limits and meaning as the [Pi launch binding](pi.md#bound-identity-committed-diff-and-file-content-for-pi-reviewers). The server reads them once at start from the `ISSWF_GIT_EVIDENCE_BINDINGS` environment variable, a JSON object keyed by those namespaces. If the variable is missing, malformed or still the literal `${ISSWF_GIT_EVIDENCE_BINDINGS}`, every tool call fails closed. The plugin, the working directory, the repository and the model cannot supply or change a binding. Claude starts plugin servers with a minimal environment and passes this one variable through from the launching process.

The binding belongs to one Claude process, not to one subagent. An Agent-tool dispatch inside the coordinator's session shares that session's server, which starts without a review binding, so it is not a bound review. Launch each review as its own process and set the variables only in that process's environment:

```sh
ISSWF_GIT_EVIDENCE_BINDINGS='{"isswf.git-evidence/1":{...},"isswf.git-evidence.diff/1":{...},"isswf.git-evidence.content/1":{...}}' \
MAX_MCP_OUTPUT_TOKENS=100000 \
claude -p --agent isswf:isswf-reviewer --plugin-dir /absolute/factory-root \
  --model <approved-model> --effort <approved-effort> \
  --allowedTools "mcp__plugin_isswf_isswf_git_evidence__identity mcp__plugin_isswf_isswf_git_evidence__diff mcp__plugin_isswf_isswf_git_evidence__content" \
  "<review task with the exact base/candidate and required checks>"
```

Fill each namespace as in the Pi guide: full commit IDs, canonical repository, trusted Git executable, `timeoutMs`, `outputBytes` and, for content, `paths`. Do not export the variable in a shell that starts other Claude sessions: every session started from that shell would be bound to the same candidate. Setting it only for one command limits that exposure but it is still a coordinator-supplied input, not an operating-system boundary. `--allowedTools` is for the non-interactive process to use those three tools without a prompt and is not a permission bypass.

Claude Code truncates MCP text beyond its token limit (default 25,000 tokens, `MAX_MCP_OUTPUT_TOKENS`) and appends an `[OUTPUT TRUNCATED` marker. The server cannot see that limit, so the no-partial-evidence guarantee requires the coordinator's `MAX_MCP_OUTPUT_TOKENS=100000` in the review process, as in the launch command above. Evidence with that marker is incomplete: treat it as a failure. The server refuses, instead of truncating, any result whose text exceeds 98,304 bytes. This usually limits content to about 40,000 raw bytes; choose a content `outputBytes` of 32,768 or less. A diff is returned in chunks of at most 24,576 bytes; every chunk states its number, the chunk count and the whole patch's byte count and SHA-256. Treat the patch as complete only when chunks 1 to `chunkCount` concatenate to that digest. Call `diff` once per chunk number. On Claude Code 2.1.312 the host may instead save a large tool result to a file and show the reviewer only a short preview with its path. The preview is not the evidence: the reviewer must read the saved file in full, and any truncation marker or incomplete read is a failure (the chunk digest rule above still decides completeness). This was observed on 2.1.312 only; other versions are unverified.

The server and the Pi invoker share one verifier. It checks provenance before returning anything (repository, base and candidate commits and binding digest for every operation; plus the Git executable for identity, the commit and path for content), canonical base64, byte count and SHA-256 for diff and content, and a refusal may omit provenance fields but must not contradict the binding. It exposes an exact UTF-8 view only when the bytes decode. A coordinator-supplied result or a synthetic fixture does not prove that the reviewer invoked a tool. The loading fixture, `tests/claude-reviewer-tools.mjs`, shows only that the host lists these three tools in the reviewer's context without a model call. Evidence tools run with Claude's host permissions and give no OS containment, as in Pi.

## Existing legacy runtime assignments

Explicitly retained legacy assignments keep their original launcher, runtime pin, release identity and checkpointed inputs under `docs/installation.md` and `docs/local-worker-lifecycle.md`. Read those guides from their retained runtime. Do not remove claims, change stores, overwrite inputs or relabel an old failure to enter the new path. Host-native adoption does not migrate an installed project's state or complete historical acceptance.
